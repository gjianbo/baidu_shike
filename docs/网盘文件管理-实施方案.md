## 三、接口契约（I / U）

> 除特别说明外，全部在隐藏 WebView 内同源 `fetch`，自动带 Cookie；写操作另需 `bdstoken`。
> 公共参数沿用现有 `api()`：`clienttype=0&app_id=250528&web=1&channel=chunlei`。

| 操作 | 方法 | URL | 表单 / 关键参数 | 期望响应 |
|---|---|---|---|---|
| 新建文件夹 | POST | `/api/create` | `path`、`isdir=1`、`block_list=[]`、`size=0` | `errno=0` |
| 重命名 / 移动 / 复制 / 删除 | POST | `/api/filemanager` | `opera=rename|move|copy|delete`、`async=0`、`filelist=[...]`、`ondup` | `errno=0` |
| 创建分享 | POST | `/share/set` | `fid_list=[fsid]`、`schannel=4`、`period`、`pwd`、`bdstoken` | `link` / `shorturl` / `pwd` |
| 群文件转存 | POST | `/api/transfer` | `shareid=<msg_id>`、`from=<owner>`、`fsidlist=[fsid]`、`path`、`ondup=newcopy`、`async=2` | `errno=0` / `taskid` |
| 预上传 | POST | `/api/create` | `path`、`size`、`isdir=0`、`rtype=2`、`block_list=[md5...]` | `uploadid` |
| 分片上传 | POST(multipart) | `/rest/2.0/pcs/superfile2` | `method=upload&type=tmpfile&path&uploadid&partseq` + 文件分片 | `errno=0` |
| 创建文件（收尾） | POST | `/api/create` | `path`、`size`、`isdir=0`、`rtype=3`、`uploadid`、`block_list` | `errno=0`、`fs_id` |

**`filelist` 结构**：
- rename：`[{"id":fsid,"path":"/a/b","newname":"c"}]`
- move：`[{"id":fsid,"path":"/a/b","dest":"/x","newname":"b"}]`
- copy：`[{"path":"/a/b","dest":"/x","newname":"b","ondup":"newcopy"}]`
- delete：`[{"id":fsid,"path":"/a/b"}]`

**上传分块规则（I）**：
- 块（block）= 256KB，用于 `block_list` 校验；
- 片（part）= 16 块 = 4MB，`superfile2` 一次上传一片；
- `block_list` 为整文件每 256KB 的 MD5 列表；`superfile2` 的二进制分片走原生 `HttpURLConnection`（同 CookieJar），因为 WebView `fetch` 不便发本地二进制。

> **验证状态说明**：`/api/list`、`/api/streaming`、`docview` 等读接口已在 `docs/已转存客户与网盘目录-技术验证.md` 真机验证（R）。本文的**写接口与上传接口尚未端到端跑通**，参数按社区/网页惯例实现，标记 **I/U**；真机首次联调时若字段有出入，改动集中在 `PanApi.kt` 一处即可。

| `MainActivity.kt` | 顶栏「新建文件夹 / 上传」入口；长按动作面板；重命名/移动/复制/删除/分享/转存/详情对话框；目录选择器；批量 移动/复制/删除；上传进度弹窗；`load()` 增加 `acceptAnyErrno` 以便读取网盘具体错误码 |

| `res/drawable/ic_folder_add.xml`（新增） | 「新建文件夹」图标（文件夹 + 加号） |

**关键设计**：

1. **复用 `load()`**：所有写请求走现有同源 fetch 通道；新增 `acceptAnyErrno=true` 让 `submitWrite` 能拿到非 0 `errno` 做友好提示（否则 `load` 会统一抛「请求失败」）。
2. **失败回滚**：写操作只有 `errno=0` 才动缓存；失败只弹提示，**不破坏已缓存列表**。成功后 `clearDisk()` + `refresh()`。
3. **二次确认**：删除、批量删除都走 `AlertDialog` 二次确认；移动/复制目标用「目录选择器」避免手输路径。
4. **身份隔离**：所有缓存 key 走 `AccountScope`，写操作只影响当前账号。

## 八、风险与未验证项（U）

1. **写接口无契约**：`/api/create`、`/api/filemanager`、`/share/set`、`/api/transfer` 属网页私有接口，前端发版可能改参数；已集中在 `PanApi`，便于单点修正。
2. **群文件转存路径（最高风险）**：群文件不是公开分享，「`/api/transfer` + `shareid=msg_id/from=owner`」是 **I/U**，需真机确认；若不通，退路是先用 `/api/list` 找到对应文件后另寻群转存接口。
3. **分片上传（I/U）**：预上传/收尾用 `/api/create` 的 `rtype=2/3` + `uploadid` 属社区惯例；`superfile2` 的 Cookie 鉴权、`partseq`、`block_list` 需真机确认。若失败，可整体替换 `PanUploader` 的上传链路而不动 UI。
4. **分享接口**：`/share/set` 的 `period`（0/1/7 天）与 `pwd` 语义需真机确认；当前实现 `pwd` 留空让网盘生成随机码。
5. **回滚粒度**：批量移动/复制只做「整体一次请求」，网盘可能部分成功；失败时以后端返回为准，刷新后再看实际状态。
6. **上传取消**：当前「后台继续」只关闭 UI，不中断后台线程；后续可加请求级取消。

## 十、审核记录（本轮自查与修复）

对已实现代码做了一轮审核，发现并修复如下问题：

1. **分片上传缺 Content-Length**：`superfile2` 的 multipart 未设长度会走 chunked，网盘可能拒收。→ 改用 `setFixedLengthStreamingMode` 精确写入 `Content-Length`（`postForm` 同样处理）。
2. **秒传/已存在被误判失败**：预上传返回 `errno=0` 但无 `uploadid` 时，原逻辑直接报错。→ 若 `return_type==1` 或已回 `fs_id`，按成功处理。
3. **`readFully` 可能死循环**：底层 `read` 返回 0 时旧逻辑不退出。→ 改为 `read <= 0` 即结束。
4. **分享请求重复公共参数**：`/share/set` 的 `clienttype/web` 与 `api()` 默认参数重复。→ 去掉重复项。
5. **`fs_id` 以字符串提交**：`fid_list` / `fsidlist` / `filelist.id` 原为字符串。→ 统一用数字（`fsidValue`，非数字回退字符串），提高接口兼容性。
6. **分享提取码为空可能被拒**：原 `pwd` 传空。→ 客户端生成 4 位随机码提交，展示时优先用服务端返回值、缺省回退生成值。
7. **登录失效提示被清空**：写操作 `onCancelled` 原会把 `status` 清空，覆盖「登录态失效」提示。→ 改为 toast 提示，不清状态。
8. **上传成功重复 toast**：成功时「已上传」+「上传完成」两次提示。→ 合并为一次。
9. **上传回调生命周期**：Activity 销毁后回调可能操作已失效 UI。→ 回调加 `isFinishing || isDestroyed` 守卫。
10. **目录选择器窗口尺寸**：`setLayout` 早于 `show()` 可能不生效。→ 先 `show()` 再设尺寸。
11. **`fileManager` 空 `ondup` 参数**：会附带无意义的空参数。→ `ondup` 为空时不拼该字段。

**修复后验证**：`gradle :app:compileDebugKotlin` 与 `:app:assembleDebug` 均 BUILD SUCCESSFUL，Debug APK 重新产出。

> 仍未端到端验证的仅剩「私有写接口 / 上传域名 / 群转存参数」这类需要真机登录态联调的部分（见第八节），属于接口事实而非代码缺陷；接口字段若有出入，改动集中在 `PanApi.kt` / `PanUploader.kt`。

## 十一、变更记录：上传功能（P2-14）已取消并移除

经复核，上传链路存在**协议层面的实质问题**，无法在无真机联调的情况下保证正确，按决策**取消上传功能、从代码中移除**。

具体问题：

1. **分块大小存疑**：实现里按「块=256KB、片=4MB」计算 `block_list`；而百度 PCS 的分片上传通常要求 `block_list` 为**每个 4MB 分片**的 MD5（块与片同尺寸）。按 256KB 计算极可能导致预上传校验/秒传失败。
2. **预上传/收尾接口选型不确定**：实现用 web 的 `/api/create`（`rtype=2/3`）承担预上传与收尾；开放平台实际是 `xpan/file?method=precreate` / `method=create`，web 端流程与 `rtype` 语义并未被验证，属猜测。
3. **上传域名与鉴权**：分片上传应走 `c.pcs.baidu.com` 等上传域名，且鉴权依赖 `access_token` 或对应域 Cookie；本 App 只有 `pan.baidu.com` 的 web Cookie，向 pcs 域名上传能否鉴权未验证。
4. **整体不可端到端验证**：上述任一处不符都会导致上传失败或产生脏数据，不适合直接上线。

处理方式：

- 删除 `PanUploader.kt`。
- 移除网盘页「上传」入口及 `startUpload / pickUploadFile / uploadFileLauncher / panUploader / uploadDialog` 等代码。
- 保留其余文件管理能力：**新建文件夹 / 重命名 / 移动 / 复制 / 删除 / 分享 / 群文件转存**（这些只依赖 `/api/create`、`/api/filemanager`、`/share/set`、`/api/transfer` 的普通参数，复杂度与风险远低于分片上传）。

后续若要恢复上传，建议改用**百度官方 Android SDK 的上传模块**（自带 access_token、分片、秒传、错误码），而不是自行拼私有 web 接口。

## 十二、删除接口实测结论：errno 132（百度安全验证）

- 实测（模拟器、已登录账号）：**新建文件夹、重命名均 `errno=0` 成功**；仅 **删除** 返回 `errno=132`：
  ```json
  {"errno":132,"info":[],"verify_scene":1,"authwidget":{"safetpl":"filemanager","saferand":"...","safesign":"..."}}
  ```
- 含义：百度对「删除文件/文件夹」这类敏感操作强制**安全验证（平台风控）**，不是参数错误，也无法用普通 API 静默完成。
- 处理：`errno==132` 时弹「需要百度安全验证」，提供「打开网盘网页」跳转，让用户完成验证/直接在网页删除后再回 App 重试；不再显示含糊的「网盘请求失败」。
- 若后续要彻底无感删除，只能依赖百度官方能力；私有 web 接口无法绕过风控。

## 十三、变更：删除功能已从 App 移除

原因：删除受百度安全验证（errno 132）强制拦截，App 内无法静默完成，只会变成「跳网页验证」，入口体验割裂。经与产品确认，**移除 App 内的删除入口**。

- 移除：长按菜单「删除」、批量选择「删除」按钮、`confirmDelete`、`PanApi.deleteItems`、相关布局与字段。
- 保留：新建文件夹、重命名、移动、复制、分享、群文件转存、收藏、详情（重命名已实测 `errno=0`）。
- 若 `errno==132` 仍从移动/复制触发，沿用「需要百度安全验证」提示 + 打开网盘网页的兜底。

## 十四、补正（2026-11-09 实测反转）：删除可直接成功 —— 新版请求形态 + `newVerify=1`

> 十二/十三的「删除一定被安全验证拦截」结论**只在旧式请求形态下成立**。改用新版网盘（`/disk/main` SPA）的请求形态后，删除可**直接 `errno=0` + `taskid`** 成功：
>
> ```json
> {"errno":0,"info":[],"request_id":339224803697953274,"taskid":99953219607539}
> ```

同为 `opera=delete`、同一 `bdstoken`，成败差异：

| 维度 | 旧式请求（errno 132） | 新版请求（errno 0） |
|---|---|---|
| `newVerify` | 不带 | **`1`（关键开关）** |
| `async` | `0` | **`2`（异步任务，返回 taskid）** |
| `onnest` | 不带 | **`fail`** |
| `filelist` | `[{"id":fsid,"path":"/a/b"}]`（对象） | **`["/绝对路径"]`（纯路径字符串数组）** |
| Cookie / 会话 | 可能不完整 | 完整新盘会话（BDUSS / STOKEN / csrfToken / PANPSC …） |
| Referer | 非必 `/disk/main` | `https://pan.baidu.com/disk/main` |

结论：

- **`newVerify=1` 是关键开关**：新版网盘客户端用它声明走新版安全验证通道，配合完整登录态，服务端把该请求判为可信新盘客户端，**不再下发旧版 `authwidget`**，直接执行删除。
- **`filelist` 用绝对路径字符串数组**即可，不再需要 `{id,path}` 对象（那是旧接口形态）。
- **`async=2`** 使删除变成后台任务、返回 `taskid`（大目录/批量更快，轮询任务状态）。
- 仍需保留 `errno==132` 兜底分支：新会话、高频、异动仍可能触发风控。

修正后的可用配方（占位，勿把凭据入库）：

```
POST https://pan.baidu.com/api/filemanager
  ?async=2&onnest=fail&opera=delete&newVerify=1
  &clienttype=0&app_id=250528&web=1&bdstoken=<token>&dp-logid=<logid>
Headers: Cookie:<完整新盘会话>
         Referer:https://pan.baidu.com/disk/main
         X-Requested-With:XMLHttpRequest
Body (application/x-www-form-urlencoded):
  filelist=["/绝对/路径"]        # 单个或多个绝对路径字符串
=> {"errno":0,"taskid":<id>}
```

> 处理：产品层可据此**恢复 App 内删除入口**（走新盘形态 + 完整会话）；`errno==132` 仅作兜底提示，不再是删除的必经门槛。
