## 一、结论（先说结果）

| 判断                   | 结论                                          |
| -------------------- | ------------------------------------------- |
| 能不能做出「能跑的 demo」      | 能。WebView 登录 + 私有 XHR + ExoPlayer 播直链，是成熟套路 |
| 能不能按文档 1-2 周交付「可用版本」 | **不能**。排期建立在「抓包顺利、群结构扁平、直链能直接喂给播放器」三个未验证假设上 |
| 能不能长期稳定 / 分发给别人用     | **不能走当前路径**。网页版私有接口无契约、无退路，且服务协议明确可封禁网盘功能   |
| 后台续播能不能达成            | 大部分能，但**不能打包票**。荣耀 MagicOS 省电管控需用户手动白名单     |
| 建议动作                 | 先做 2-3 天 Spike（见第三节），三个验证点全绿再排期             |

**一句话**：架构骨架（Kotlin + Media3 + MediaSessionService + Room）选得对，错的是「接口层」和「播放链」这两层——文档把它们写成了「抓包确认参数即可」，实际是「逆向签名 + 两套互斥的鉴权/流媒体体系」。

## 二、数据源形态定案（2026-11-07 需求方确认，歧义已关闭）

### 2.1 是「IM 群组文件库」，不是「分享」

需求方 2026-11-07 明确：**「群组文件库，不是分享」**。结合此前抓包，形态定案如下：

| 维度     | 定案                                                                                                                                                                                                    |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 产品形态   | 百度网盘**网页版 IM 群组文件库**（`doc_lib`，挂在通讯录会话上），当前 `bb18`、`得到帆书课程`，以后会增加（10.8 动态库）                                                                                                                           |
| 文件归属   | **群主 / 他人上传**，用户侧是引用（`owner_uk` + `fs_id`），不占自己空间 —— 这正是「几百 T」能成立的原因，也是 10.11 播放限制的关键背景                                                                                                               |
| 入口路由   | `disk/main#/im/addrBook` → `#/im/session?fromId=...`                                                                                                                                                  |
| 实证接口族  | `/imbox/file/recentv2`（跨库最近更新）、`/mbox/group/listshare`（单库根目录列表）、`/mbox/msg/shareinfo`（目录逐级下钻）、`/sharedir/file/dirsize`（目录大小辅助）、`/pfile/mboxvideo` + `/mbox/msg/mediainfo` + `/mbox/msg/streaming`（播放） |
| 鉴权     | 网页登录态 Cookie + 公共参数组（`channel=chunlei` / `clienttype=0` / `web=1` / `app_id=250528`）；**只有 `dirsize` 另需 `bdstoken` + `time` + `sign`**，`recentv2` / `listshare` / `shareinfo` 都不需要，**逐接口确认，不可推广**      |
| 库稳定 ID | **`gid`（17 位数字）** —— 实证 `session_id = "04_" + gid`，见 10.14                                                                                                                                            |
| 交叉佐证   | `from_doc_lib=true`、`download_source=im`、埋点 `webHashPath=/disk/main#/im/session`                                                                                                                      |

**明确排除（原交底文档里写错的部分）**：分享链接体系**全部不适用** —— `/s/1xxx` 链接、提取码、`shareid` / `uk`（作分享标识）、`/share/verify`、`/share/list`、`/api/sharedownload`、`sign`+`timestamp` 那套分享鉴权、官方《获取分享链接音视频文件流数据》(`/rest/2.0/xpan/share?method=streaming`)。开发不要按这套去写 `PanApiClient`。

> ⚠️ 但 `owner_uk` / `from_uk` 里的 `uk` 是**上传者账号标识**，不是分享链接的 `uk` 参数，别一起排除掉；10.9 已实证 `from_uk` 与 `dirsize` 请求体的 `owner_uk` 相同，是拼播放参数的必需字段。

> **2026-11-07 更正记录（保留以免沿用旧结论）**：
>
> 1. 初稿据「个人版群组约 20 人、空间随创建者容量（SVIP 上限 30T）」推断「几百 T 单群不成立，更像分享链接集合」——**已撤销**。文件库是引用式，不占自己空间，几百 T 完全成立。
> 2. 初稿把 `/mbox/...` 判为「旧版线索、已被 `/sharedir/file/*` 取代」——**已撤销**（见 10.9）。实测是**分工关系**：`sharedir` 管目录辅助，`mbox` / `pfile` 管音视频播放，新版前端两套并存。
> 3. **10:31 第四处更正**：第 2 条里附带的「老教程 `/mbox/group/listshare` 仍不要照抄」——**也已撤销**。需求方实测 `GET /mbox/group/listshare` 正是当前版本（前端 `2026_11_05`）的**单库根目录列表**接口，与 `POST /mbox/msg/shareinfo` 组成目录树。详见 10.14。**至此 `/mbox/*` 三支都已实证在用：`group/listshare`（根）、`msg/shareinfo`（下钻）、`msg/mediainfo` + `msg/streaming`（播放）。**
> 4. **09:48 命名归类更正**：此前把「群组文件库」这个名字让给了开放平台 `gid` 那套（形态 a），把实测形态命名为「共享文件夹 (c)」，写成「实际形态是 (c)，不是 (a)/(b)」——**这个表述会误导**。用户说的「群组文件库」与实测的 `imbox`/`sharedir`/`mbox` 是**同一个东西**，`sharedir` 只是它的底层引用模型，不是独立产品形态；(a) 则应改称「开放平台 gid 群组服务」，见 2.2。**接口层判断没错，错的是把产品名判给了另一套体系。**

**仍需两份完整 HAR**（文件列表页一份 + 播放器新标签页一份），确定列表响应字段与播放链路，见 10.7 / 10.9 抓包指引。

### 2.2 ⚠️ 同名不同物：开放平台的「群组文件库」不是这个

第五节的开放平台《群组文件消费》里也有「群组文件库列表」，但那是**另一套体系**：

|         | 本项目用的：网页版 IM 群组文件库                                             | 开放平台「群组文件消费」                     |
| ------- | -------------------------------------------------------------- | -------------------------------- |
| 标识      | `gid`（17 位群 ID）/ `msg_id` / `from_uk` / `fs_id` / `session_id` | 同为 `gid` / `shareid` / `fid` 等命名 |
| 鉴权      | 网页登录态 Cookie                                                   | OAuth `access_token`             |
| 接口前缀    | `/imbox/*`、`/sharedir/*`、`/mbox/*`、`/pfile/*`                  | `/rest/2.0/xpan/...`             |
| 获取方式    | 现成网页功能，抓包即可                                                    | 实名认证 + 创建应用 + **商务采购**（第五节）      |
| 本项目是否适用 | ✅ 是，唯一数据源                                                      | ❌ 否（自用侧载，不做商务采购）                 |

**开发最容易踩的坑**：看到「群组文件库」四个字就去查开放平台文档、去申请 OAuth gid 接口 —— 名字一样，接口体系、鉴权、准入完全不同。本项目的接口契约**只以 10.7～10.14 抓到的网页私有 XHR 为准**。

> ⚠️ **10:31 精确化（别把上表读歪）**：`gid` 这个**参数名并非开放平台专属** —— 10.14 实测 `GET /mbox/group/listshare?...&gid=...` 与 `POST /mbox/msg/shareinfo?...&gid=...` 都在用 `gid`，但走的是**网页 Cookie** 鉴权、`/mbox/*` 前缀。要排除的是「开放平台那套 `gid` + `access_token` + `/rest/2.0/xpan/...` + 商务采购」，**不是 `gid` 这个字段本身**。本项目的库主键就是用 `gid`。同理 `shareinfo` 是接口路径名，不代表走「分享链接」体系。

### 2.3 「不下载」的定义

在线流播放必然有缓冲。ExoPlayer 不配置 `SimpleCache` 时只有内存缓冲，可做到「不落文件」；但建议把口径写死为「不写用户可见存储、不生成持久缓存文件」，避免验收时争议。

## 三、三个 go/no-go 前置验证（Spike，2-3 天）

不要先写业务代码，先用一份最小脚本 + 一个最小播放器验证三件事：

| #  | 验证项                                      | 验收标准（可复现）                                                                                                | 失败时的影响                     |
| -- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------- |
| V1 | 用真实账号抓一次群文件页的全部 XHR，还原「列最新 N 条」的完整请求     | 拿到完整 HAR；用 OkHttp/curl **脱离浏览器**重放成功，返回 `errno=0` 且含 `server_mtime`；连续 3 次、间隔 1 小时重放均成功                  | 失败 → 说明有设备指纹/签名绑定，方案退化     |
| V2 | 拿到一个音频文件的可播直链，在 Android 真机用 ExoPlayer 播通 | 自定义 `DefaultHttpDataSource.Factory` 注入 UA/Referer/Cookie 后，`STATE_READY` 且能连续播 10 分钟；seek、302 跨域、切网络各测一次 | 失败 → 整个播放链重做               |
| V3 | 荣耀真机后台续播 30 分钟                           | 锁屏 / 切后台 / 关屏 / 移动数据 四种组合各 30 分钟不断流，通知栏可控；记录是否需手动白名单                                                     | 失败 → 核心痛点（后台续播）无法达成，产品价值归零 |

V1 要特别确认：**`sign` 是能从页面 DOM/JS 上下文直接取值，还是需要逆向算法**。若需逆向，工作量与长期维护成本要单独评估。

## 四、逐条核查：文档哪些对、哪些错

证据等级：**A** = 厂商官方文档/协议原文；**B** = 通用技术事实/官方文档可推导；**C** = 二手资料，仅作线索、需实测。

| #  | 文档中的说法                                              | 核查结果                                                                                                                                                                                                                                                                                           | 证据                                              |
| -- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 1  | 复用 BDUSS/STOKEN + Referer 即可复刻 XHR                  | **不足**。网页版接口普遍还需 `bdstoken`（从首页 HTML 提取、会话级）、`app_id=250528`、`channel=chunlei`、`clienttype=0`、`web=1`，分享类接口另需 `sign`+`timestamp`                                                                                                                                                               | C（需 V1 实测）                                      |
| 2  | `filemetas` / `sharedownload` 拿 dlink 播 mp3/m4a/mp4 | **部分错**。官方 `filemetas` 用 `access_token`（OAuth），不是 BDUSS，且面向**自己盘内**文件；群分享文件走 `sharedownload`（shareid/uk/sign/timestamp/fs_id）。网页版私有 `/api/filemetas` 才是 Cookie 体系                                                                                                                              | A（官方 filemetas/查询文件信息文档）                        |
| 3  | dlink 同时支持 m3u8                                     | **错**。m3u8 是独立转码流接口：官方 `GET /rest/2.0/xpan/share?method=streaming`，`type=M3U8_MP3_128`（音频）/ `M3U8_AUTO_480` 等，需 `access_token`+`sign`+`devuid`+`uk`+`shareid`+`fid`。dlink 是原始文件直链，产不出 m3u8。**2026-11-07 实证补充**：网页版 IM/文件库场景走的是私有链路 `/mbox/msg/streaming?...&stream_type=M3U8_AUTO_480`（见 10.9） | A（官方「获取分享链接音视频文件流数据」）+ A（本次抓包） + C（第三方脚本线索）     |
| 4  | `media3-exoplayer` 即可                               | **漏依赖**。播 m3u8 必须加 `media3-exoplayer-hls`                                                                                                                                                                                                                                                      | B                                               |
| 5  | 直链不缓存、播前实时获取                                        | **不够**。官方明确 dlink 有效期 8 小时、必须带 `User-Agent: pan.baidu.com`，错误码 31326（防盗链）/31360（过期）/31045（token）。「暂停几小时后再续播」必然遇到 URL 失效，需要「重取 URL + 重建 MediaItem + seek 回原 position」的断点续播设计                                                                                                                    | A（官方「下载」文档）                                     |
| 6  | 首页按 mtime 倒序展示最近更新                                  | **架构缺口（已基本补上）**。群文件是「文件库 → 多个分享 → 每个分享分页列表」的模型，全局时间倒序需递归/增量拉取；官方递归 listall 有明确频控（31034，≤8-10 次/分钟）；Room 只写「进度/列表缓存」，缺增量同步与游标。**2026-11-07 补**：实测网盘自带 `/imbox/file/recentv2` 聚合接口（10.10），首屏可直接取「最近更新」，不必自己递归；仍需确认响应是否含 `server_mtime` / 播放凭据 / `cursor`                                         | A（官方 doclist）+ A（本次抓包）                          |

### 5.3 官方合规路径是存在的（重要）

百度网盘开放平台有「**群组文件消费**」能力，功能清单包含：群组文件库列表、获取群分享详情、获取某个分享文件列表、文件库分类列表/消息列表、转存系列、**获取点对点音视频信息**、**视频播放 streaming**。

> ⚠️ **2026-11-07 形态定案后的适用性说明（2.2 / 10.12）**：需求方已确认数据源是**网页版 IM 群组文件库**，不是分享链接。本节的「群组文件消费」是开放平台 **gid + OAuth + 商务采购**体系，与本项目实测的 `imbox` / `sharedir` / `mbox` 私有 XHR **同名不同物**；保留本节**仅为说明「将来若要分发时的合规出路」**，本项目（自用侧载）**不申请、不接入、不照抄**它的接口。同理，《获取分享链接音视频文件流数据》属于分享链接体系，也不是本项目当前的播放链路（当前是 `/mbox/msg/streaming`）。

## 六、修订后的实施路径

### 阶段 0：Spike（2-3 天，go/no-go）

见第三节 V1/V2/V3。产出：HAR 文件、可重放的请求脚本、真机播放验证录屏、荣耀后台 30 分钟日志。**三个全绿才继续。**

### 阶段 1：接口层与鉴权（原 P1+P2 合并，约 1 周）

- 数据源形态已定案为 **IM 群组文件库**（2.1），只实现这一套；分享链接体系与开放平台 gid 体系一律不接
- `PanApiClient` 内聚 `bdstoken` 刷新、`sign` 取值、Cookie 注入、错误码映射、退避重试
- Cookie 加密存储；登录失效为显式重登流程
- 增量同步：`mtime` 游标 + 本地快照 + 频控预算，首屏只拉增量


### 阶段 2：播放链（原 P3+P4 合并，约 1-1.5 周）

- `MediaSessionService` + `mediaPlayback` FGS type + `POST_NOTIFICATIONS` 引导
- 自定义 `DefaultHttpDataSource.Factory`（UA/Referer/Cookie/302）
- 音频走 dlink（mp3/m4a）、视频走 streaming m3u8 + `media3-exoplayer-hls`，**两条链路分开实现**
- URL 失效重取 + 断点续播；进度写 Room（5 秒节流，改为「暂停/切轨/退出时 + 每 15 秒」更省电）
- 荣耀/MagicOS 白名单引导页 + 真机矩阵验收

### 阶段 3：联调与异常态（约 1 周）

- negative tests：Cookie 过期、dlink 403、频控 31034/errno -9、离线、通知权限被拒、后台被杀、切网
- 「今日新更/未听」基于本地快照计算，不额外请求

**乐观估计 3-4 周**（Spike 通过后），且需预留接口改版的长期维护预算。原 1-2 周只在「抓包顺利 + 群结构扁平 + 只做音频」时成立。

### 10.2 关键简化：用「WebView 同源代发 XHR」替代「OkHttp 脱离浏览器复刻」

这是自用边界带来的最大红利，也是相对原方案最重要的架构修改。

**原方案**：抓包 → 还原全部参数 → 原生重放 → 逆向 `bdstoken` / `sign` → 维护 UA/Cookie/指纹一致性。  
**新方案**：App 内保留一个 WebView 加载群文件页，**让页面自己的 JS 发 XHR**，结果通过 JS bridge 回传 Kotlin。

| 收益                                   | 原因                        |
| ------------------------------------ | ------------------------- |
| 不用逆向 `sign`、不用还原 `bdstoken` 生成逻辑     | 参数由百度自己的页面脚本生成，天然正确       |
| 不用维护 UA / Referer / Cookie / 设备指纹一致性 | 请求就是浏览器发的，与真人一致           |
| 接口改版时大部分参数自动跟随                       | 页面升级即参数升级，只需适配返回的 JSON 结构 |
| 不用做完整抓包与请求重放                         | 只需观察返回结构                  |

**代价与边界（必须接受）**：

1. WebView 只在 App 前台可靠存活，**后台播放期间不能依赖它发请求**；
2. 播放链仍是原生的 —— dlink 必须交给 ExoPlayer，用自定义 `DefaultHttpDataSource.Factory` 注入 `User-Agent: pan.baidu.com` / Referer / Cookie；
3. 首屏要等群文件页加载完（约 1-3 秒），用缓存的 Room 快照先渲染、WebView 结果回来再刷新。

### 10.3 修正后的最小架构

```
LoginActivity（一次性）
  └─ WebView 登录 → CookieManager 取 BDUSS/STOKEN → 加密存 DataStore（仅作后台兜底）
        │
PanWebView（前台取数，同源）
  ├─ 注入 JS 调页面自身 XHR → ① 文件库列表 ② 选中库的「最近更新」+ dlink/播放参数
  │  JS bridge 回传 JSON
  ▼
LibraryRepository（Room：FileLibrary 表）
  └─ 动态库清单（稳定 ID / 名称 / 启用 / 排序 / 每库独立 lastSyncMtime 游标）
        ▼
QueueRepository（Room）
  └─ 按 libId 分区的列表快照 + 跨库归并的「全部」视图
     + 播放进度 + 已听标记 + 每条 URL 的过期时间
        ▼
PlaybackService（MediaSessionService + ExoPlayer，自定义 DataSource）
  └─ 前台服务 / 通知栏 / 锁屏 / 音频焦点；播放队列一次装填，后台不再依赖 WebView
```

**播放与过期的处理**（自用可接受的简化）：每次打开 App 时在前台一次性解析好今日全部条目的可播 URL，连同过期时间装进播放队列；后台播放期间 URL 失效就**暂停并提示回到 App 刷新**，不做静默热更新、不做无缝重连。对 1-2 小时的课程完全够用，省掉原方案最麻烦的「重取 URL + 重建 MediaItem + seek 续播」。

**明确砍掉**：**复杂多库管理页**（只保留自动发现 + 启用/隐藏 + 排序，见 10.8）、搜索过滤、小部件、荣耀快捷指令、账号体系、完整错误态 UI、任何云同步/推送/统计 SDK（「无服务端」要贯彻到底，别把自用工具变成数据外发）。

> ⚠️ **「视频 / m3u8 / `media3-exoplayer-hls` 放二期」这一条已撤回**。10.9 实证：点开 mp4 走的是 HLS 转码流而非原始直链，且真实目录里存在大量 mp4。是否砍视频取决于需求方对 10.9.4 的回答；`media3-exoplayer-hls` 是否必需还取决于**音频是否也走 streaming**（Spike V4）。**V4 出结论前，不要按「只做音频 + dlink」把架构锁死** —— 10.3 架构图里的「dlink / 播放参数」应保持两种形态都能装。

## 10.8 文件库必须动态可选（2026-11-07 需求修正）

需求方明确：`bb18`、`得到帆书课程` 是**当前**的两个，以后会增加，不能写死。**上一版「两个固定 tab、砍掉多群管理」的结论作废**；10.1 / 10.3 / 10.7 中相关表述已同步修订。

### 10.8.1 产品行为（默认方案）

| 项 | 设计 |
|---|---|
| 库从哪来 | **自动发现**：每次启动 / 下拉刷新时让 WebView 拉取网盘侧的文件库列表，diff 出新库并提示「发现新文件库：XXX，是否加入首页」 |
| 怎么选 | 首页顶部横向切换器 + 「全部」视图；可**启用/隐藏**每个库、拖动排序，不要求用户手动输入 ID |
| 默认视图 | 「全部」：跨所有启用库按 `server_mtime` 归并倒序；可切到单库视图 |
| 持久化 | Room `FileLibrary` 表：`id / name / type / enabled / sortOrder / lastSyncMtime`；**新增 `WatchRoot` 表**：`rootId / libId(gid) / fs_id / path / depth / enabled`，见 10.14 |
| 主键（库级） | ✅ **定案：用 `gid`（17 位数字）**。10.14 实证 `session_id = "04_" + gid`，而 `gid` 同时出现在 `listshare`（库根目录）与 `shareinfo`（下钻）里，是跨接口稳定、跨层级不变的库标识。**绝不用名称、数组下标或 `session_id` 全串** —— 后者带 `04_` 前缀，前缀是否固定未验证。`to`（19 位，播放页会话 ID）、埋点 `fromId`（9 位，通讯录联系人 ID）与 `gid` 是三个不同的东西，别混用。V0 里「稳定 ID 待抓包确认」这一项**已关闭** |
| 增量游标 | 若 `recentv2` 响应带 `cursor` / `has_more`（10.10），优先用接口游标做增量同步，比本地 `server_mtime` 过滤更可靠；`id=2` 语义未确认，可能是分类或分页参数，别当常量写死。**10.14 后游标改为按 `WatchRoot` 分区**，比按库分区更细 |
| **收听根目录** | 库内是多级目录（10.14 实证至少 2 级下钻，实测路径可达 6 层）。用户**一次选定**关注的末级目录存为 `WatchRoot`，首页「最近更新」只对这些根各取一页后归并。**请求量从「递归全库」变为 O(N 订阅根)，N 由用户控制**；不做后台预取、不做全量递归 |
| 主键（条目级） | 10.9 显示播放凭据含 `msg_id`，属**消息级**而非纯文件级。条目主键建议 `(libId, fs_id)` 或 `(to, msg_id, fs_id)` 组合，并把 `to` / `msg_id` / `from_uk` 一并存下（播放时要拼 streaming 参数），**不能只存 `fs_id`** |

> **唯一需要需求方拍板的点**：新发现的库默认启用还是默认不启用？建议**默认不启用**，避免新库突然灌进首页；用户确认后再加入。

### 10.8.2 对架构的四处影响

| # | 变化 | 说明 |
|---|---|---|
| 1 | 多一个接口 | 需要抓「文件库列表」接口（进入通讯录/会话列表时的请求），不只是 `/sharedir/file/dirsize`。已加 Spike 项 **V0** 和抓包步骤第 2 步 |
| 2 | 增量游标从 1 个变 N 个 | `lastSyncMtime` 按 `libId` 分区存；新库从 0 全量拉一次，之后走增量 |
| 3 | 「最近更新」变跨库归并 | 各库分别取 `mtime > lastSync` 的增量 → 本地按 `server_mtime` 归并排序 → 渲染「全部」；不是把 N 个列表简单拼接 |
| 4 | **请求量变 O(N)，频控风险回归（10.10 后下调但不消失）** | 库变多后必须：只对 `enabled` 的库同步、**串行 + 间隔**、带 `mtime` 过滤、仅前台启动/下拉时同步，**不做后台定时轮询、不并发**（官方 `listall` 频控 31034，≤8-10 次/分钟）。10.10 找到 `recentv2` 后**去掉了目录深度这个乘数**，且若该接口一次返回全部会话则降为 O(1)；在响应字段实测前仍按 O(N) 保守设计 |

### 10.8.3 排期与验收

- 增量约 **+2-3 天**（库列表接口 + 选择 UI + 跨库聚合 + 每库游标 + 新库 diff），总排期由 2 周调整为 **2-2.5 周**。
- 补充 negative tests：
  - 新增一个库后能自动发现，且不覆盖已有库的进度；
  - 隐藏某库后「全部」视图不再出现其条目，但其播放进度仍保留；
  - 某库请求失败（403 / 超时）不影响其他库与已缓存内容；
  - 库增至 5 个时启动同步为串行、无频控错误码；
  - 网盘侧删除某库后 App 不崩溃，标记为不可见而非丢数据。

### 10.8.4 与 WebView 代发方案的关系

动态化反而**更适合** 10.2 的方案：库列表由网盘页面自己渲染和请求，App 不需要维护任何硬编码 ID 或群号；页面新增了库，WebView 拿到的列表自然多一条。代价只是多一个 JS bridge 回调和一张 Room 表，**不需要改回原生复刻**。

> 注意：这仍属于「只自己用」的边界内 —— 动态化是数据源可扩展性，不是多用户/多账号，不引入账号体系或服务端。

## 10.9 视频播放链路实证：`pfile/mboxvideo` + HLS 转码流（2026-11-07 第三次修订）

需求方点开一个 mp4 后，百度**跳新标签**打开了 `GET /pfile/mboxvideo?...`。这条线索解开了此前一直空白的播放链路，也**推翻了 2.1 的「`/mbox/...` 已是旧版链路」判断**。

### 10.9.1 先定性：这不是可播直链

`pfile/mboxvideo` 是 **pan.baidu.com 域下的 HTML 播放器页面路由**（第三方油猴脚本靠把 `pfile` 改写成 `play/video#` 来适配，正是这条路由存在的旁证）。它：

- **不能**直接喂给 ExoPlayer —— 需要登录态，返回的是页面；
- **不是** `d.pcs.baidu.com/...` 的 dlink；
- 在新标签打开，说明百度把「列表浏览」和「音视频播放」拆成了两套页面/请求体系。

**参数解析**（只列参数名与语义，具体值不复述、不落盘）：

| 参数 | 语义 | 对 App 的意义 |
|---|---|---|
| `from_doc_lib=true` | 来自**文件库** | 确证数据源是 IM 群组文件库（doc_lib），不是分享链接（2.1 / 10.12） |
| `download_source=im` | 来源是 **IM 消息附件** | 播放体系属 mbox（消息箱），不是自己网盘目录、也不是 `/share/*` 分享链路 |
| `to` | 19 位会话/群组 ID | **库级稳定 ID 的新候选**；与埋点里的 `fromId`（9 位）不是同一物，别混用 |
| `from_uk` | 发送者 uk | 与 `dirsize` 请求体里的 `owner_uk` 相同，两条证据交叉印证 |
| `msg_id` | IM 消息 ID | **消息级**标识 —— 播放参数是「文件 + 所在消息」的绑定，不是纯 `fs_id` |
| `fs_id` / `name` / `size` | 文件 ID / 文件名 / 约 36 MB | 条目主键与展示信息 |
| `type` | 类型标记（本例为 `2`） | **语义未确认，不要猜**，V4 实测 |
| `path` | 完整 6 层目录：`/纪录片/更新/2025年4月/科学实验/科普/…/xxx.mp4` | 按 年/月/主题/课程 分层，**不是扁平列表** |
| `selection_cursor` | 09:23:00 CST（毫秒时间戳） | 前端选中态游标，是时间不是 token |
| `to_ciduk` / `from_ciduk` / `imTransferBlock` | 空值 | 模板参数，暂无作用 |
| URL 结尾悬空 `&` | 模板拼接痕迹 | 说明参数可能没贴全，**一切以 HAR 为准** |

### 10.9.2 播放链路（C 级线索 + 本次 A 级证据交叉）

第三方脚本的 `pfilevideo` 分支显示，播放页内部这样取流：

```
GET /pfile/mboxvideo?...            ← HTML 播放页（新标签），不是直链
  ├─ GET /mbox/msg/mediainfo?from_uk&to&msg_id&fs_id&type
  │       → JSON：resolution / adToken 等
  └─ GET /mbox/msg/streaming?from_uk&to&msg_id&fs_id&type&stream_type=M3U8_AUTO_480
          → #EXTM3U 播放列表（TS 分片，非 mp4）
```

**关键推论**：拼 streaming 接口所需的参数，几乎就是播放页 URL 里那几个（`from_uk` / `to` / `msg_id` / `fs_id` / `type`）。也就是说——**播放地址很可能可以由列表字段直接拼出，不需要逆向 `sign`**。这对 10.2 的 WebView 代发方案是利好。

但先别乐观，三个未确认项：

1. 脚本里还有 `adToken`（来自 mediainfo）、`isplayer=1`、`check_blue=1`，以及 `errno=133` 的广告 token 分支 —— **哪些是必需参数，必须 V4 抓包定死**；
2. 该线索来自第三方油猴脚本（C 级），与当前前端版本是否一致未验证；
3. 官方 FAQ 佐证了 HLS 形态：m3u8 分片链接有效期 **8 小时**、浏览器有跨域限制（建议自建客户端播放）、Web 不支持 mpegts，**原生 App 用 ExoPlayer HLS 是正确方向**。

### 10.9.3 对方案的影响

| # | 变化 | 处理 |
|---|---|---|
| 1 | **「`/mbox/...` 已降级为旧版」判断撤销** | 两套是分工：`/sharedir/file/*` 管目录与列表，`/pfile/mboxvideo` + `/mbox/msg/streaming` 管播放。2.1 已更正 |

## 10.10 首屏数据源定案：`GET /imbox/file/recentv2`（2026-11-07 09:37）

### 10.10.1 先定性：这是 XHR，不是页面

需求方口语说「列表的页面」，但 cURL 的 header 把性质定死了：

| 证据 | 结论 |
|---|---|
| `Accept: application/json, text/plain, */*` | 期望 JSON 数据 |
| `X-Requested-With: XMLHttpRequest` | 前端 XHR |
| `Sec-Fetch-Dest: empty` / `Sec-Fetch-Mode: cors` / `Sec-Fetch-Site: same-origin` | 同源 fetch，非文档导航 |
| 无 `--data-raw`，参数全在 query | GET 请求 |
| `Referer: .../disk/main?_at_=...` | 由网盘主页面发起 |

**即：这是返回 JSON 的「最近更新」数据接口**，上一轮「是页面路由还是 XHR」的歧义消除。首屏数据源找到了。

### 10.10.2 参数、鉴权与两个未确认项

| 参数 | 语义 | 注意 |
|---|---|---|
| `session_id` | 会话 ID（`04_` 前缀 + 17 位） | ✅ **10:31 定案**：数字部分**就是 `gid`**（10.14 实证 `listshare` / `shareinfo` 里的 `gid` 与之完全相同），即 `session_id = "04_" + gid`。所以稳定性担忧收敛为：数字部分稳定，`04_` 前缀是否随登录变化未验证。**库主键直接用 `gid`，不要用 `session_id` 全串**（10.8.1） |
| `id=2` | **语义未确认** | 可能是分类 / tab / 分页参数，不要猜、不要当常量写死 |
| `dp-logid` / `logId` | 埋点追踪 | `logId` base64 解码为 `16576859199120.31628731317309433`，是前端日志 ID，**不是凭据**；`dp-logid` 与 `dirsize` 那条差 66，同会话连续请求 |
| `channel=chunlei` / `clienttype=0` / `web=1` / `app_id=250528` | 公共参数组 | 与 `dirsize` 一致 |
| **无 `bdstoken` / `time` / `sign`** | 该接口只靠 Cookie 鉴权 | 与 `dirsize`（带全套签名）不同。**不能推广**，每个接口单独确认 |

### 10.10.3 接口族完整图景（🔄 10:31 第四处更正后）

```
【最近更新视图】
/imbox/file/recentv2              → 跨库「最近更新」聚合（首屏数据源，10.10）

【目录树视图】★ 10:31 新增
/mbox/group/listshare?gid=...     → 单库根目录列表（GET，limit=50&desc=1）
/mbox/msg/shareinfo?gid=...&fs_id=... → 逐级下钻（POST 空 body，只换 fs_id）
   └─ 同一棵树共享 from_uk / msg_id / gid，仅 fs_id 随层级变化

【辅助】
/sharedir/file/dirsize            → 共享目录辅助信息（目录大小），不是列表接口

【播放链路】
/pfile/mboxvideo
  ├─ /mbox/msg/mediainfo
  └─ /mbox/msg/streaming          → HLS 转码流（10.9）
```

10.7 把 `sharedir` 当作「列表族」是过度推断 —— `dirsize` 只是算目录大小，已更正。**10:31 更正**：此前认为 `/mbox/group/listshare` 是「老教程里的旧版线索、不要照抄」，实测它在当前版本（前端 `2026_11_05`）就是**库根目录列表**；「最近更新」与「目录树」是**并行的两个视图**，不是谁取代谁 —— `recentv2` 给跨库聚合首屏，`listshare` + `shareinfo` 给用户主动选目录。`v2` 后缀说明 `recentv2` 有版本迭代，长期维护要留意 `recent` / `recentv2` 并存与切换。详见 10.14。

### 10.10.4 对方案的四点影响

| # | 影响 | 处理 |
|---|---|---|
| 1 | ✅ **补上最大架构缺口** | 第四节第 6 条、10.7.2 一直担心的「全局按 mtime 倒序要递归全库」，现在网盘自带「最近更新」聚合视图，首屏一步拿到，不必自己遍历 6 层目录 |
| 2 | ✅ **频控回撤** | 10.9.3 第 5 条「O(N 库 × 目录深度)」→ **O(N 会话)**；若 `session_id` 可省略表示「全部」则接近 O(1)。10.8.2 的「串行 + 间隔 + 只对 enabled 库」仍保留 |
| 3 | ✅ **这个接口鉴权更轻** | 至少 `recentv2` 不带 sign/bdstoken，WebView 同源代发更简单；但**别据此假设播放接口也一样** |
| 4 | ⚠️ **新增五项验证** | ① `session_id` 重登后是否变化；② 响应是否含 `server_mtime` / `fs_id` / 播放凭据（`msg_id` / `to` / `from_uk` 或 dlink）；③ 是否有 `cursor` / `has_more`（**有游标就用接口游标做增量，比本地 `server_mtime` 过滤可靠**）；④ `id` 换值 / `session_id` 省略各返回什么；⑤ 一次请求是否覆盖多个会话（决定 O(1) 还是 O(N)） |

> 目前**只有请求侧证据，响应字段全靠推测**。脱敏 HAR 报告会列出字段名与结构，这一步决定 V1' 能否绿灯。

| 2 | 网页版 · 群组文件库 · 点**视频** | 能播（`pfile/mboxvideo` → `/mbox/msg/streaming` HLS，10.9） | 网页端对**同库文件**有在线播放能力 |
| 3 | **官方 App** · 同一批群文件库音频 | **能播** | **服务端对群组文件库音频确实返回可播地址** |
| 4 | 转存到自己网盘后 · 点音频 | **能播** | 文件本身无格式 / 权限问题；同时验证了 B1 退路的地基 |

### 10.13.2 判定逻辑

**排除 (b)**：若后端按「文件归群主、用户只是引用」禁止在线播，则同一文件在**官方 App 内也必然播不了**。App 能播是决定性的反证 —— 说明限制发生在**网页版 IM 文件库的音频 UI 入口**，不在服务端播放能力层。10.12.4 曾据「引用式模型」推断 (b) 概率上升，该推断**被实测推翻**。

**因此**：

- 「不下载 + 不转存 + 在线流」可以三者同时成立，**方案 A 方向确认**；
- 10.11 的红灯**降级为黄灯**，10.1 的「可以实施 / 2-2.5 周」**解冻**；
- 10.5 的 B1 从「唯一可行路径」**降回可选退路**；
- 群主目录名「★★★不会保存和下载，看这个★★★」现在更像是**教新手在线播放**，不再能用来推断「群期望转存后看」。

> ⚠️ **但不要把好消息说过头**：「服务端有能力」≠「我们的 App 能拿到那条地址」。官方 App 的播放请求可能带客户端专属参数（App token、设备标识、客户端版本号、签名），**网页版 Cookie 未必能复用**。10.3 的「WebView 同源代发」在列表与视频上成立，**在音频上尚未验证**。这是最后一个 go/no-go，命名 **V6**。

### 10.13.3 V6：音频可播地址怎么拿（新总闸门，按成本排序试）

| 路径 | 做法 | 门槛 / 注意 | 通过标准 |
|---|---|---|---|
| **V6-a（最轻，先做）** | 在 WebView 里**同源代发** `/mbox/msg/streaming`，对音频文件试 `stream_type=M3U8_MP3_128`（官方开放平台文档里的音频档名，**C 级线索，需实测**）；并对音频调一次 `/mbox/msg/mediainfo` 看返回结构；另试 `pfile/mboxvideo?type=1` 是否存在音频分支 | 零额外工具，纯 JS 注入即可。`type=2` 语义此前未定，「1=音频」只是**假设，不是结论**；若接口只认视频消息 ID，此路不通 | 返回可播 URL（m3u8 或 dlink），真机能播 10 分钟 |
| **V6-b（黄金路径，最关键）** | **抓官方 App 打开群文件库音频时的 HTTPS 请求** —— 既然它已证实能播，其请求形态就是最可靠的答案。重点记：接口路径、参数**名**、鉴权头是 Cookie 还是 App token / 设备标识、响应是 dlink 还是 m3u8 | Android 7+ 默认不信任用户 CA，真机需 root / Magisk 模块 / 可调试模拟器；百度 App 可能有**证书绑定**。**更省事的替代：抓 PC 版百度网盘客户端**（系统证书可装）或 Android 模拟器 + mitmproxy。**用小号**，输出只留路径与参数名，值一律不落盘 | 明确音频取址接口，并判断能否在 WebView 内复现 |
| **V6-c（保底）** | 试 `filemetas` / `dlink` 类接口对群组文件库**引用文件**是否返回直链，带 `User-Agent: pan.baidu.com` + Cookie 直连 | 引用的是他人原文件，dlink 可能不返回；若返回则最省事，沿用原方案的自定义 DataSource | 拿到 dlink 且 302 后能播 |

**判定**：任一路径拿到地址并通过 V2（真机播 10 分钟 + seek + 切网）→ V6 通过，音频链路定案。**三条全失败才启用 B1**（已由证据 4 验证地基）。

> **架构影响要提前想清楚**：若 V6-b 发现官方 App 走的是**完全不同的鉴权体系**（App token / 设备绑定），10.3 的「WebView 同源代发」在音频这一环可能失效，需要改成「原生复刻 App 播放请求」或「App 内 WebView 注入 App 专属参数」。即便如此，也不必回到逆向 `sign` 的老路 —— App 接口未必带 `bdstoken`/`sign`。**V6-b 出结果前，10.3 架构图里的「dlink / 播放参数」继续保持两种形态都能装。**
>
> 一个最低成本的中间形态（不推荐默认）：列表与进度留在自己 App，点条目用 deep link 拉起官方 App 播放。零逆向，但失去自定义续播与通知栏控制，且后台续播归官方 App 管，等于放弃了原始痛点的一半。仅作 V6 全失败时的过渡。

## 10.14 📁 目录树实证：原型缺「选择目录」，库稳定 ID 定案为 `gid`（2026-11-07 10:31）

> ⚠️ **10:45 真实 HAR 报告修正了本节两处推断，以 10.15 为准**：① `listshare` 不是「根目录文件夹列表」，而是**库内分享消息列表**（`records.msg_list[].file_list[]`）；② 「播放凭据是树级常量、可在 WatchRoot 存一次」不成立 —— `recentv2` **每条记录自带** `gid` / `msg_id` / `fuk`。其余结论（逐级下钻只换 `fs_id`、`gid` 定案、订阅根设计、原型缺口）均成立。

### 10.14.1 需求方的问题

> 「这个原型图还有一种情况，就是目录，很多级，比如得到帆书课程……是不是还少一个选择目录的功能」

**结论：是，而且缺的不是「一个按钮」，是三处联动。** 原型的 6 屏全部假设「列表是扁平的」——首页只有 `/imbox/file/recentv2` 的最近更新 + 库筛选，没有任何进入目录树的入口。但真实数据是按 年/月/主题/课程 分层（10.9 实证 `path` 有 6 层），用户想听某个特定栏目、或想指定「从哪个目录开始算今天的新更」时，现有原型完全无路可走。

### 10.14.2 三条请求解出的四件事

| # | 实证 | 结论 |
|---|---|---|
| 1 | `GET /mbox/group/listshare?...&gid=...&limit=50&desc=1` | **这是当前版本的「库内分享消息列表」接口**（`records.msg_list[].file_list[]`，10.15 真实 HAR 修正；此前写成「根目录文件夹列表」不准确）。2.1 更正记录里「老教程的 `listshare` 不要照抄」是**第四处误判，已撤销**。只靠 Cookie，无 `bdstoken` / `sign` |
| 2 | `POST /mbox/msg/shareinfo?...&fs_id=A&...` → 再一条 `fs_id=B`，**其余 `from_uk` / `msg_id` / `gid` / `type` / `page` / `num` / `limit` / `desc` 全部相同**，空 body | **逐级下钻 = 只换 `fs_id`**。整棵目录树共享同一条根消息（`from_uk` + `msg_id` + `gid` 是树级常量）；带 `page` / `num` / `limit` 分页与 `desc` 排序 |
| 3 | `recentv2` 的 `session_id` = `04_` + 17 位数字，该数字与 `listshare` / `shareinfo` 的 **`gid` 完全相同** | **库稳定 ID 定案为 `gid`（17 位）**。10.8.1「稳定 ID 待抓包确认」、10.10.2「`session_id` 可能重登就变」两项**一并关闭**。仍别用 `session_id` 全串（前缀是否固定未验证），也别混用 `to`（19 位）/ 埋点 `fromId`（9 位） |
| 4 | 三条 `dp-logid` 依次相差 4、6，同会话连续点击 | 是「根目录 → 一级 → 二级」的真实操作序列，不是跨会话拼接 |

**「最近更新」与「目录树」是并行的两个视图，不是谁取代谁**：`recentv2` 给跨库聚合首屏（一步打开），`listshare` + `shareinfo` 给用户主动选目录。10.10.3 的接口族图已补全。

> 两个仍未确认、别写死的点：① `desc=1` 在 `listshare` / `shareinfo` 上是按什么字段倒序（若就是 `server_mtime`，**中间层目录可能已能直接给时间倒序文件，用户不必下钻到末级** —— V7 重点）；② `type=2` 语义（与 `pfile/mboxvideo` 的 `type=2` 同名，可能是「群组文件库」类型常量），不要猜。

### 10.14.3 原型要补的三处

| # | 位置 | 补什么 |
|---|---|---|
| 1 | **新增第 7 屏「目录浏览」** | 面包屑（可点回退）、目录项 / 文件项视觉区分、逐级下钻、返回上级、层级深度提示、「加载更多」分页、**「把当前目录设为收听根」** 主操作 |
| 2 | **首页加入口** | 现在只有「最近更新」+ 库筛选 chip；加「浏览目录」入口，并让首页显示当前生效的订阅根数量（如「2 个收听根」），让用户知道「今日新更」是从哪些目录算出来的 |
| 3 | **库管理屏加配置** | 每个库显示/编辑自己的收听根目录。**逐级目录是配置一次的动作，不该每次打开 App 都点 6 层**；新库默认不启用且无订阅根 |

### 10.14.4 关键设计：把「选目录」做成**订阅根**，不是纯浏览

这是本轮真正的产品增量，也顺带收敛了 10.8.2 的频控担忧：

```
用户一次选定关注的目录 → WatchRoot(libId=gid, fs_id, path, depth, enabled, autoFollowLatest)
        │
        ▼
首页「最近更新」只对每个 WatchRoot 取一页（shareinfo / recentv2），本地跨根按 server_mtime 归并
        │
        ▼
请求量 = O(N 订阅根)，N 由用户控制；不做后台预取、不做全量递归、串行 + 间隔
```

| 收益 | 说明 |
|---|---|
| 频控收敛 | 10.8.2 的「O(N 库)」升级为**更可控的 O(N 订阅根)**；用户选 2-3 个根就是 2-3 次请求，不随目录深度增长 |
| 一步打开不破 | 配置一次后，日常仍是打开即看；目录浏览只在想改范围时才进 |
| 语义更准 | 「今日新更」变成「我关注的那几个目录的新更」，不会被整个库里的老教程视频灌满 |
| 动态库兼容 | 新库默认不启用 + 无订阅根，不会突然灌进首页（10.8 的拍板建议保持） |

**数据模型**（Room）：

| 表 | 字段 |
|---|---|
| `FileLibrary` | `id` = **gid** / `name` / `enabled` / `sortOrder` / `lastSyncMtime` |
| `WatchRoot` | `rootId` / `libId(gid)` / `fs_id` / `path` / `depth` / `enabled` / `autoFollowLatest` / `lastSyncMtime` |
| 目录浏览缓存 | **仅前台会话内存**，不持久化整棵树 —— 库有几百 T、目录会变，落盘全量树既不必要又会过期 |

**边界要处理**：群主新建了「2026年12月」这类月份目录时，原来的订阅根会漏更新。两个选项：① `autoFollowLatest=true`（每次同步时按 `server_mtime` 自动把根切到最新子目录）；② 提示「检测到新目录，是否切换」。**不要静默递归全树**。另外目录被删/改名时 `fs_id` 失效要能提示重选，不能崩。

> ⚠️ **不能就此宣布 V6 通过**：工具只输出字段名不输出值，`dlink` 有可能是空串、占位、或对引用文件返回空。必须做 **V6-d**：取一条**音频文件**的 `dlink` 值 → 带 `User-Agent: pan.baidu.com` + Cookie 直连 → 看 HTTP 状态 / `Content-Type` / 302 → 真机 ExoPlayer 播 10 分钟。同时按官方规则验 8 小时有效期与 `31326` / `31360` 错误码。
>
> **V6 优先级重排**：`V6-d（读列表 dlink）` → `V6-a（试 streaming 音频档）` → `V6-b（抓官方 App）` → `V6-c（filemetas）`。10.13.3 与 10.14.8 的「先做 V6-a」口径以本条为准。若 V6-d 通过，**Spike 可省掉抓官方 App 的那 1 天，排期回到 2-2.5 周 + 目录屏 1-2 天**。

### 10.15.2 字段名两套体系不一致，归一化层必须存在

| 语义 | `recentv2` 里 | `shareinfo` / `listshare` 里 |
|---|---|---|
| 文件 ID | `fsid`（str）；`meta.fs_id`（str） | `fs_id`（int） |
| 上传者 | `fuk`（int） | query 里的 `from_uk`；`listshare` 里叫 `uk` |
| 是否还有下一页 | `data.hasmore`（bool） | `has_more`（int） |
| 分页游标 | `newno`、每条 `time` | `page` / `num` / `limit` / `last_msg_time` / `timestamp` |
| 列表容器 | `data.recentlist[]` | `records[]`；`listshare` 的 `records` 是**对象**（`msg_count` + `msg_list[]`） |

**两个必须改的设计**：① **别共用同一个 DTO**，做一层 `PanFile` 归一化；② 10.8.1 / 10.10 反复假设的「`cursor` / `has_more` 游标」**实际不存在** —— `recentv2` 用 `data.hasmore` + `newno`，`shareinfo` 用 `has_more` + `page`。增量同步游标改按这些字段设计（具体取哪个仍要看值，报告不输出值）。

另外 `recentv2` 的 `meta` 里所有字段都是 **str**（`server_mtime` / `size` / `isdir` 全是字符串），而 `shareinfo` 的 `records` 里同名字段是 **int**。解析时别直接当数字用。

### 10.15.3 `listshare` 不是「根目录文件夹列表」，是**群分享消息列表**（修正 10.14.2 第 1 条）

真实响应结构：

```
records (对象)
  ├─ msg_count
  └─ msg_list[]
       ├─ msg_id / group_id / msg_type / msg_ctime / msg_content
       ├─ uk / uname / nick_name / avatar_url
       └─ file_list[]   ← 每条消息带一组文件/文件夹（含 isdir / path / server_filename）
```

即「文件库」的真实模型是 **群 → 多条分享消息 → 每条消息带一棵文件树**。`shareinfo` 需要 `from_uk` + `msg_id`，正是**展开某一条群消息里的文件树**，而不是「在库根目录里换文件夹」。

**对原型的影响**：目录屏第一级应是「**更新批次 / 消息**」（带日期、发送者、文件数），点进去才是文件夹层级。10.14.3 与原型第 7 屏已按此修正。

**对 10.14.5 第 4 条的修正**：我上一轮写「播放凭据是树级常量、可在 WatchRoot 存一次」—— **不准确**。`recentv2` 的每条 `recentlist[]` 自身就带 `gid` / `msg_id` / `fuk` / `fsid` / `path` / `parent_path` / `share_root_path`，即**每条记录自带完整播放参数**，无需从树级继承。这反而更简单：条目按 `(gid, msg_id, fsid)` 存即可，播放参数直接可取。

### 10.15.4 面包屑与订阅根可以直接用响应字段

`recentlist[]` 里有 `path` / `parent_path` / `share_root_path` / `time` / `uname` —— **不用自己拼目录路径**。10.14.4 的 `WatchRoot.path` 可以直接落 `path` 或 `share_root_path`，面包屑用 `path` 分段即可，不必在客户端维护深度计数。

`meta` 里还有 `black_tag` / `block_list` / `videotag` / `real_category` / `file_key` / `source` / `status` —— **`black_tag` / `block_list` 很可能与「暂不支持播放」有关**（是否命中黑名单 / 版权拦截）。报告不输出值，下一步看这两项的具体值，可能解释为什么音频被拒、视频能播。

### 10.15.5 其余结构结论

| 发现 | 处理 |
|---|---|
| `/sharedir/file/dirsize` → `data.taskid`，`/sharedir/file/dirsizetask` → `progress` / `status` / `dirlist` / `task_errno` | **两步异步任务**，用来算目录大小，不是列表接口。App 不需要它（不显示目录体积），别轮询、别计入请求量 |
| 报告未发现播放链路请求（`pfile` / `streaming` / `mediainfo` 都没有） | 这次 HAR 没点开 mp4，或没导播放器新标签那份。**10.9 的 HLS 视频链路仍有效但未被本次佐证**；V4 视频部分仍待补抓 |
| `/api/analytics`（6 条）、`/ztbox`（6 条）、`/aiknowledgeapi/record/notice`（1 条）都是埋点 | 已加入 `NOISE_PATH` 排除，下一版报告会更干净 |
| `recentv2` 顶层有 `newno` / `show_msg`，`listshare` 有 `last_msg_time` | 可作为「是否有新消息」的轻量判断，但先别依赖，值语义未验证 |

### 10.15.6 结论变化

| 项 | 10:31 口径 | 10:45 口径 |
|---|---|---|
| V6 总闸门 | 三条候选都未验证，先试 streaming | 🔑 **最可能已解**：列表响应带 `dlink`，只差直连实测 |
| Spike 工期 | 2-3 天（含抓官方 App +1 天） | 若 V6-d 通过可省 1 天 |
| 库稳定 ID | `gid`（已定案） | ✅ 报告里 `recentlist[].gid` 再次佐证，**彻底定案** |
| 字段模型 | 假设 `fs_id` / `cursor` / `has_more` 一套 | ⚠️ **两套字段名 + 两套类型**，必须做归一化 |
| 目录第一级 | 当作文件夹 | **群分享消息批次**（`msg_list` + `file_list`） |
| 原型第 7 屏 | 已加 | 第一级改为「更新批次」；标注文件项自带 dlink |

## 10.16 ⭐ 收藏：常听栏目 / 单条的快速入口（2026-11-07 10:57）

> 需求方原话：「**还少一块就是收藏，我同步听几个栏目或视频，不能每次都从目录中筛选吧**」

### 10.16.1 为什么不能拿「订阅根」直接代替

上一轮（10.14）做的 `WatchRoot` 解决的是「**今日新更从哪算**」，是数据源范围；这轮要的是「**我现在在追哪几个**」，是快速入口。两者语义不同，硬合并会让首页既臃肿又难用：

| | 订阅根 `WatchRoot` | 收藏 `Favorite` |
|---|---|---|
| 语义 | 数据源范围（聚合口径） | 快速入口（每天点几次） |
| 粒度 | 只有**目录** | **目录（栏目）或单条内容** |
| 数量 | 可以较多，用户不常看 | **少而精**，建议 ≤8，超出提示归档 |
| 是否影响「今日新更」 | ✅ 是 | ❌ 否，只影响首页快捷区 |
| 是否存进度 | ❌ | ✅ 单条收藏显示续播进度 |
| 新库 / 新条目默认 | 无 | 无 |
| 默认排序 | 按库 | **置顶 + 最近播放**，跨库混排 |

**用户真实场景**：同时跟 `bb18` 的 Day 系列、`得到帆书课程` 的每日更新、外加某个单独的 mp4 教程。三者跨库、两种粒度，每次都进目录树翻 6 层显然不行 —— 首页要有一排卡片一步直达。

### 10.16.2 两种粒度与主键

| 类型 | 收藏对象 | 卡片显示 | 点击行为 |
|---|---|---|---|
| `FOLDER` | 目录 / 栏目（`fs_id` + `path`） | 栏目名、来源库、**今日新更 N**、未听 M | 打开该栏目视图（可复用目录屏并定位到该节点） |
| `ITEM` | 单条音频或视频（`msg_id` + `fsid`） | 标题、来源库、**上次听到 12:34 / 42:16** | 直接进播放页并自动续播 |

**主键一律用 `(gid, msg_id, fsid)` 三元组**（10.15.3 已证每条 `recentlist[]` 自带这三个字段），**绝不用名称或列表下标** —— 群主改名、新增库、排序变化都不能让收藏和已听进度错位。进度继续复用现有 `PlaybackProgress` 表，不在 `Favorite` 里重复存。

### 10.16.3 与订阅根的三条联动规则（避免概念打架）

1. **收藏一个 `FOLDER` 时，自动把该目录也加入 `WatchRoot`** —— 否则收藏卡片里的「今日新更 N」没有数据来源。UI 要明示「已收藏，并已加入收听根」，别静默改数据源。
2. **取消收藏时，不自动移除订阅根** —— 用户可能只是不想在首页看到这张卡，仍希望它计入最近更新。若确实要一起删，给二次确认「同时移除收听根？」。
3. **收藏 `ITEM` 不影响订阅根** —— 单条内容不需要聚合口径。

**反向**：用户在库管理里删掉一个订阅根时，若存在对应收藏，提示「该栏目已收藏，是否一并取消」，不要留一张永远显示 0 更新的死卡。

### 10.16.4 数据模型（Room）

| 表 | 字段 |
|---|---|
| `Favorite` | `favId` / `libId(gid)` / `type(FOLDER\|ITEM)` / `fs_id` / `fsid` / `msg_id` / `from_uk` / `title` / `path` / `sortOrder` / `pinned` / `createdAt` / `lastPlayedAt` |
| 复用 | `PlaybackProgress`（按 `gid + msg_id + fsid`）、`FileLibrary`、`WatchRoot` |

`newCount` / `unheard` **不落盘**，由本地快照算（同 10.8.1 的统计口径），避免多一份会过期的数据。目录失效时（`fs_id` 404 / 被群主删掉）卡片标「已失效」并提供一键移除，**不能崩、不能静默消失**。

### 10.16.5 首页信息架构（顺序调整）

```
统计卡（今日新更 / 未听 / 已听）
⭐ 我的收藏 —— 横向卡片条，2-4 个常听项，「全部」进收藏屏   ← 新增，放在最显眼处
继续收听（上次那条）
库筛选 chips（全部 / bb18 / 得到帆书课程 / 浏览目录 / 管理库）
最近更新列表
```

收藏区放在「继续收听」**之上**：前者是「同时跟几个」，后者是「上次那一集」，前者使用频率更高。收藏为空时整块隐藏，不占位置。

### 10.16.6 原型新增四处入口 + 第 8 屏

| # | 位置 | 补什么 |
|---|---|---|
| 1 | **新增第 8 屏「我的收藏」** | 栏目卡 / 单条卡混排、置顶、取消收藏、空态引导「去目录里收藏一个栏目」、概念说明 |
| 2 | 首页 | 收藏横向卡片条 + 计数 + 「全部」入口；列表每条加星标可就地收藏 |
| 3 | 目录浏览屏 | 底部加「收藏此目录」（同时联动订阅根），与「设为根」「返回上级」并列 |
| 4 | 播放页 | 「收藏本条」按钮，已收藏时显示实心星标 |

> 列表里的星标用可点击 `<span role="button">` 而非 `<button>` —— `.item` 本身已是 button，**嵌套 button 是非法 HTML**，会让浏览器自动重排 DOM。

### 10.16.7 边界与验收

| 项 | 要求 |
|---|---|
| 跨库 | 收藏混排，按「置顶 → 最近播放」排，不按库分组 |
| 上限 | 建议 ≤8；超出提示「把不常听的归档」，不做无限列表 |
| 失效 | 库被删 / 目录失效 → 标「已失效」+ 一键移除，不崩、不丢其他收藏 |
| 主键 | `(gid, msg_id, fsid)`；改名、新增库、排序变化不导致进度错位 |
| 与订阅根 | 收藏目录自动加根；取消收藏不动根；删根时提示是否一并取消收藏 |
| 不做 | 收藏夹分组/标签、云端同步、分享收藏、收藏数统计上报（「无服务端」贯彻到底） |

**negative tests**：空收藏时首页不显示收藏区；取消收藏后首页卡片与计数同步；收藏目录后订阅根计数 +1；取消收藏后订阅根不变；删除订阅根时对应收藏有提示；收藏单条不影响订阅根；8 个以上给出归档提示；失效目录不导致启动崩溃；B1 形态下收藏行为一致。

### 10.16.8 排期与依赖

- **实现 +1 天**（第 8 屏 + `Favorite` 表 + 首页卡片条 + 三处入口 + 联动规则），总计约 **3 周**（原 2.5-3 周）。若 V6-d 通过省掉抓官方 App 的 1 天，仍约 2.5-3 周。
- **收藏不依赖 V6-d**：它是纯本地状态 + 列表数据，可与 V6 并行开发，不增加 go/no-go 风险。唯一依赖是「今日新更 N」需要订阅根同步成功，而订阅根只依赖 10.15 已拿到的列表接口。

### 10.16.9 下一步

V6-d 仍是唯一技术闸门（10.15.7）；收藏属产品形态，可以直接按本节落地，不必等 Spike。仍需需求方拍板 **10.9.4 的 A/B/C**。

## 10.17 💾 元数据缓存：课程内容不会变，缓存「目录与文件清单」

> 需求方：「我们是不是可以缓存一下那个目录下的文件？很多课程是已经存在的、课程内容不会改变」

### 10.17.1 先划清边界：缓存的是元数据，不是媒体

原需求「不下载、不落本地存储」针对的是**几百 T 的音视频内容**。这里缓存的只是文件名 / ID / 时间 / 大小这类清单数据，几万条也就几十 MB，不违背红线。

| ✅ 可以缓存 | ❌ 绝不缓存 |
|---|---|
| 文件节点元数据、目录树结构、订阅根快照、每库同步游标、收藏、逐条进度 | 音频 / 视频字节、`dlink`、m3u8 / TS 分片、任何播放凭据 |

> 🔴 **最容易踩的坑：`dlink` 绝不能缓存**。官方明确 8 小时有效期且必须带 `User-Agent: pan.baidu.com`（错误码 31326 / 31360）。缓存 URL 会在「暂停几小时再续播」时直接 403 —— 必须**播前实时取、失败重取**。同理 HLS 的 m3u8 与分片也不落盘。

### 10.17.2 三层缓存策略

| 层 | 内容 | 失效策略 | 理由 |
|---|---|---|---|
| **L1 永久** | 已存在文件节点 `FileNode(gid, msg_id, fsid, path, server_filename, server_mtime, size, isdir, category, parent_path, md5)` | 按 `(gid,msg_id,fsid)` 内容寻址 upsert，**不设 TTL** | 课程内容不可变，只有新增；已有的条目永远不用再问服务端 |
| **L2 会话 / 短 TTL** | 目录树结构、排序结果、订阅根快照、`recentv2` 聚合结果 | 启动时按 `lastSyncMtime` / `newno` 校验，变了才重建 | 结构会变（群主新建月份目录、改名、删文件） |
| **L3 不缓存** | `dlink` / streaming URL / m3u8 / TS / 播放凭据 | 播前实时取 | 有效期 + 风控 + 302 |

### 10.17.3 增量同步（呼应频控底线）

- **首次**：只拉元数据、不拉媒体，按订阅根逐层，**串行 + 间隔**；不做全库扫描（10.8.2 / 10.14.4）。
- **之后**：带 `lastSyncMtime` 或 `newno`（10.15.2 实证的分页字段）只取增量，本地按 `server_mtime` 归并。
- **触发**：仅启动 / 下拉刷新；**不做后台定时轮询**（官方 `listall` 频控 31034，建议 ≤8-10 次/分钟）。
- **收益**：请求量从「每次打开 O(N 订阅根 × 页数)」降到「通常 1 次增量」；首页「一步打开」不再依赖网络也能出内容。
- **失效处理**：文件被删/改名 → 404 时标 `stale` 并局部刷新；目录层级变了按 `path` 重建；**不静默丢缓存**，界面显示「显示的是上次同步内容」。

### 10.17.4 离线能力

| 完全离线可用 | 需要网络 |
|---|---|
| 最近更新列表、收藏、目录浏览（已缓存部分）、已听进度、所有 UI 状态 | ① 检查新更；② 播放（实时取 `dlink`） |

离线态 UI：显示「离线 · 显示缓存内容」+ 上次同步时间，**不弹错误、不阻塞浏览**。

### 10.17.5 存储量与风险（数值为估算，需实测）

按 10 万条 × 约 300 B ≈ **30 MB**，Room 完全可接受。**估算值，不作为结论**。不做全量文本索引、不存响应原文（避免把私有目录名之外的东西落盘）。

| 风险 | 处理 |
|---|---|
| 缓存让「最新」有延迟 | 明确刷新策略 + 界面常显上次同步时间；下拉手动刷新 |
| 课程被替换（同名同 `path` 但内容变） | 比对 `md5` / `size` / `server_mtime`，变了更新节点；**进度按 `fsid` 保留**并提示「内容已更新」 |
| 与「不批量扒库」冲突 | 只缓存用户选定订阅根下的元数据，永不递归全库 |
| 缓存污染 / 版本升级 | `FileNode` 表带 schema version，接口字段变化时可局部重建而非清空全部 |

## 10.18 ⏱ 逐条播放进度：每条音视频都能续播

> 需求方：「有没有可能记录每个视频或音频的播放位置？每个都可以继续播放」

### 10.18.1 现状缺口

原交底只写「每 5 秒记录当前 position → Room」，**没说记到哪一条**；原型此前也是单一全局播放状态，只有一条「继续收听」。用户要的是**按条目持久化**，音频和视频一视同仁。

### 10.18.2 数据模型

```
PlaybackProgress(
  gid, msg_id, fsid,          -- 复合主键，10.15.3 已证每条 recentlist[] 自带
  positionMs, durationMs,
  mediaType,                  -- AUDIO | VIDEO，共用一张表
  updatedAt, completed
)
```

- 主键用 `(gid, msg_id, fsid)`，**绝不用标题或列表下标** —— 群主改名、新增库、排序变化都不能让进度错位。
- 与 `Favorite` / `WatchRoot` **完全独立**：取消收藏、删订阅根、隐藏库都**不删进度**（10.16.3 的联动规则只管数据源，不碰进度）。

### 10.18.3 写入时机（防丢）

播放中每 **5 秒** + 暂停 / seek / 切条目 / 切后台 / 退出 App 时各写一次。**不能只在 `onStop` 写** —— 后台被系统回收会丢最后一段。播完置 `completed=true`，`positionMs` 建议保留（便于「重听」），但续播规则不命中。

### 10.18.4 续播规则

| 条件 | 行为 |
|---|---|
| `0 < positionMs < durationMs - 30s` | 自动续播，播放页提示「已从 mm:ss 续播」 |
| 接近结尾（剩余 <30s）或 `completed` | 从头播，列表标「已听」 |
| 列表展示 | 每条显示进度条 + 百分比 / 已听徽标 |
| 首页 | 「继续收听」仍是最近一条，另显示「N 条可续播」 |
| **`dlink` 过期重取后** | 用新 URL **seek 到同一 `positionMs`**，不要从头开始 |

### 10.18.5 边界与验收

- `positionMs` 是**媒体时间**，不是墙钟时间 —— 倍速、缓冲、HLS 分片、302 跨域都不应影响语义。
- 视频切后台只保留音轨时进度照记（10.9.4 的 B 情况）。
- 无服务端 → 多端不共享进度，符合自用边界，不做同步。
- **negative tests**：连切 5 条各停在不同位置 → 逐条重开位置正确；播完标已听且不再自动续播；取消收藏后进度仍在；目录失效条目进度不丢；离线打开能看到进度；`dlink` 重取后 seek 生效。

## 10.21 💾 本地备份与误删恢复

> 需求方：「再加一个备份，本地的就可以，防止误删后，还需要重新配置」

### 10.21.1 三层防护（对准「误删」这个真实痛点）

| 层 | 做法 | 解决什么 |
|---|---|---|
| 1 | **软删除 + 撤销**：删除收藏 / 订阅根 / 库时先标 `deletedAt`，10 秒内可撤销，不做物理删除 | 手滑误删，最高频 |
| 2 | **自动本地快照**：每次配置变更后去抖写一份 JSON，保留最近 **3 份** | 撤销窗口过了、或连续误操作 |
| 3 | **手动导出 / 导入**：SAF `ACTION_CREATE_DOCUMENT` / `ACTION_OPEN_DOCUMENT`，单文件存本机 | 换机、重装、灾难恢复 |

### 10.21.2 备份内容（6 类）

| 类别 | 关键字段 |
|---|---|
| `FileLibrary` | `gid` / `name` / `enabled` / `sortOrder` / `lastSyncMtime` |
| `WatchRoot` | `libId(gid)` / `fs_id` / `path` / `depth` / `autoFollowLatest` |
| `Favorite` | `type` / `fsid` / `msg_id` / `path` / `sortOrder` / `pinned` / `lastPlayedAt` |
| `PlaybackProgress` | 逐条 `positionMs` / `durationMs` / `completed` / `updatedAt` |
| `Preferences` | 主题、形态 A/B1、仅 Wi-Fi、倍速、同步策略 |
| `SyncCursor` | `newno` / `lastSyncMtime` / `schemaVersion` |

**🔴 绝不备份**：Cookie / `BDUSS` / `STOKEN` / `csrfToken` / `bdstoken` / `sign`（安全）、`dlink` / m3u8 / TS（8 小时有效期，备份即失效）、任何媒体文件（不下载红线）。

**不需要备份**：10.17 的 L1/L2 元数据缓存清单 —— 可从网盘重建，备份它只会让文件变大且可能过期。

> **恢复后仍需登录一次**（Cookie 不在备份内），这是设计而非缺陷；界面要明确提示，别让用户以为备份坏了。

### 10.21.3 文件形态

```json
{
  "schemaVersion": 1,
  "app": "one-tap-listen",
  "exportedAt": "...",
  "libraries": [], "watchRoots": [], "favorites": [],
  "progress": [], "preferences": {}, "syncCursor": {}
}
```

单文件约几十 KB，**纯本地、不上传、无服务端、不加密**（自用边界）。但含私有目录名，导出时提示「别外发」。

### 10.21.4 恢复流程

1. 选文件 → 校验 `schemaVersion` + `app` 标识 → 解析失败明确报错，**不写一半**；
2. **预览**：将恢复几类、各多少条、会覆盖什么；
3. **二次确认**；
4. Room **单事务**写入，失败整体回滚；
5. 按 `(gid, msg_id, fsid)` 合并；**进度取 `updatedAt` 较新者，不倒退**；收藏 / 订阅根按稳定 ID 去重；
6. 重建索引、刷新首页，提示「登录态需重新验证」。

### 10.21.5 边界与验收

- 不做云备份 / 跨设备同步 / 账号体系（「无服务端」贯彻到底）。
- 自动快照：保留 3 份、连续操作去抖只写一次、写失败静默等下一轮，**不阻塞 UI**。
- **negative tests**：备份文件里不含任何凭据字段；导入损坏 JSON 不崩且现有数据不变；旧 schema 明确拒绝或迁移；恢复后进度不倒退；撤销删除后收藏与订阅根计数一致；离线可备份 / 恢复；主题偏好能被恢复；恢复过程不中断后台播放。

### 10.21.6 排期与可裁剪范围

主题 **+1 天**、备份 **+1-2 天**，合计 **+2-3 天 → 约 4-4.5 周**（V6-d 通过省 1 天）。两项都不依赖 V6-d，可并行。

> **工期紧时建议裁剪**：备份先只做「软删除 + 撤销 + 自动快照」两层（已覆盖误删主诉求），**手动导出 / 导入放二期**，可省约 1 天。主题因为已经用语义 token 实现，成本最低，不建议砍。

## 10.22 首页信息层级修订（2026-11-07 12:50，需求方看图提问后）

### 10.22.1 需求方原话

> 「全部 / bb18 筛选条、目录入口、收藏区，这不和下面重叠了吗？要不要优化一下？首页是不是应该加每个课程的播放进度，可以直接点继续播放？」

### 10.22.2 结论：不是 DOM 重叠，是三类「视觉重叠」

逐个查了原型与样式，**没有任何元素真的压在列表上**（无绝对定位叠层、无负 margin），但确实有三处会让人读成「重叠 / 挤在一起」：

| 现象 | 真实原因 | 处置 |
| --- | --- | --- |
| 「管理库」被切掉一半，收藏第三张卡只剩一条白边 | 两处都是**横向滚动容器末端硬裁**，没有渐隐，也没有「右边还有」的暗示 | 筛选条只留 2 项（见 10.22.7），不再溢出；收藏条改 `mask-image` 真淡出（JS 判断还有没有更多，滚到底就取消渐隐） |
| 筛选条像被塞进列表卡片里 | `.chips` 下边距只有 12px，紧接着就是列表卡的 `border-top`，两条线几乎贴着；且筛选条是**全宽**而列表卡**内缩 18px**，线比卡宽 | 筛选条改**吸顶**（sticky）；目录 / 管理库入口从筛选条里移出，改放顶部图标；吸顶时用 JS 补一条分隔线（`is-stuck`），静止时用卡片自己的上边框，避免双线 |
| 首屏只看到 1 条更新 | 从状态栏到列表之间堆了 6 层：缓存提示条 → 三宫格统计 → 收藏标题 → 收藏横条 → 继续收听卡 → 筛选条 | 删掉常驻缓存提示条（降为列表末尾一行小字）、三宫格压成一行统计、继续收听提到最上面做大卡 |

**判断标准**：这是「首屏预算」问题，不是「组件重叠」问题。首屏每多堆 100px，就少看见 1.3 条更新，而「打开就看到今天更了什么」是本 App 的第一价值。

### 10.22.3 首页新顺序（自上而下）

1. **标题 + 目录 / 同步两个图标**
2. **继续收听大卡**（橙色，唯一强调块）：标题、`已听 12:34 / 42:16`、`剩余 29:42`、白色进度条，点整卡即从该位置续播；无进度时整卡隐藏
3. **一行统计**：`3 今日新更 · 2 未听 · 12 已听`（原三宫格，高度 78px → 20px）
4. **我的收藏**：横向卡片（栏目 + 单条混排），右端渐隐
5. **吸顶筛选条**：`全部 / 未听 N` —— 按「听没听」筛，不按库筛（10.22.7）
6. **最近更新列表**：按 今天 / 昨天 / 更早 分组
7. 列表末尾一行小字：`列表已缓存 · 仅增量同步 · N 条可续播`

**移走的两个入口**：「浏览目录」→ 顶部文件夹图标（Tab Bar 里也有「目录」）；「管理库」→ 只在设置页与目录屏保留。理由：它们是**导航**，不是**筛选**，混在一行里既让用户误判语义，又会把这两个入口滚动出屏幕。

### 10.22.4 逐条播放进度：从「三套并存」收敛成一套

修订前的实现有三种进度表达，彼此不一致：

| 位置 | 形态 | 问题 |
| --- | --- | --- |
| 列表项 body 内手工 `.item-prog` | 46px 短条（62%、34%） | 只有部分条目有，且不随播放更新 |
| 列表项 side 内 JS 注入的 `.row-prog` | 44px 短条 + 百分比文字 | 与上面那条同时存在，同一条目出现两条进度 |
| 继续收听卡 | 硬编码文案「12:34 / 42:16」 | 与 `PlaybackProgress` 无关，播哪条都不变 |

**收敛后只保留一套**：
- 列表项第 2 行**跨整行**的 3px 进度条（从标题左边缘起，与图标右侧对齐）+ 右侧文字「已听 12:34 · 剩 29:42」；
- 完成态整条转绿 + 文案「已听完」；
- 数据全部由 `PlaybackProgress`（`(gid, msg_id, fsid)`）驱动，继续收听卡读同一条记录；
- 右侧只留**一个**星标（收藏），不再竖排堆「新更 / mp3 / 62% / 星」四样东西 —— 这是标题被截断的真正原因。

**点击语义**：点条目任意位置 = 从该条自己的位置续播；点星标 = 只收藏、不播放（事件在星标处截断）。

### 10.22.5 验收标准（可直接照着写 UI 测试）

- 首屏（390×820）至少完整可见 **3 条**更新，且「继续收听」卡与「最近更新」列表在同一屏内；
- 筛选条滚动时**吸顶**，列表从其下方穿过；静止与吸顶两种状态都**只有一条**分隔线；
- 收藏条只有 2.5 张卡可见，第 3 张**淡出**而非硬切；滚到底后不再淡化最后一张；
- 任意条目进度条、时间文案、`meta` 里的时长三者**数值自洽**（`已听 + 剩余 = 总时长`）；
- 最近播放的条目变化后，「继续收听」卡标题与进度跟着变；无任何进度时整卡不显示；
- 暗黑模式下：继续收听卡保持橙色强调、收藏条淡出正常、迷你播放器与 Tab Bar 均为深色。

### 10.22.6 对排期与实现的影响

**不影响接口层，不影响 V6-d**，全部是 Compose 布局层级问题，成本约 **0.5 天**（含吸顶状态与渐隐判断）。但有一条实现约束要写进任务卡：

> Compose 里用 `LazyColumn` + `stickyHeader` 实现筛选条吸顶，**不要**用 `Column + verticalScroll` 套 `LazyColumn`（会失去懒加载）；收藏横条用 `LazyRow` + 末端 `Brush.horizontalGradient` 遮罩，遮罩只在 `canScrollForward` 时绘制。

### 10.22.7 按库筛选 → 按「未听」筛选（需求方 13:21 拍板）

需求方看了眼筛选条问「这一块有什么用」，答案是：**现在几乎没用**。

| 为什么现在的按库筛选不成立 | 说明 |
| --- | --- |
| 只有 2 个库 | 当天总共 3 条，「全部」与「bb18」的差别只是少 2 条 |
| 信息重复 | 每条列表的 meta 已写明来源库（`bb18 · mp3 · 28:04`） |
| 诉求已被覆盖 | 「只看某个栏目」由收藏的栏目卡承担，且能直达目录 |
| 真正成立的条件 | 库 ≥ 4，或某个库日更 10+ 条会淹掉其他库 —— 现在都不是 |

**改为 `全部 / 未听 N`**：同一个位置、同样的高度，但筛的是**用户打开 App 的目的**——「今天有没有新的、我还没听的」。库维度交给条目 meta 与收藏；库数涨到 4 个以上再把库筛选作为第三项加回。

配套口径：
- `未听` 包含「没播过」和「听到一半」，`已听` 只算 `completed`，两者都对 `PlaybackProgress` 取反，不额外存状态；
- 筛选条上的数字（`未听 5`）与顶部统计行的「未听 5」**同源**，不允许两处各算一套；
- 一条播完后若正处在「未听」筛选下，该条**立即移出列表**，顶部数字同步 −1（原型已实现，见 `applyListFilter` / `syncCounts`）。

## 10.23 首页横条：收藏 → 最近播放（2026-11-07 13:30，需求方提）

### 10.23.1 需求方原话

> 「首页中我的收藏，能换成最近播放吗？应该可以看其他课程的视频课。」

两句话其实是**一个因果**：收藏是「我要长期跟的几个栏目」，容量只有 8 个、要手动维护；而用户真实的日常动作是「昨天那节视频课看到一半，今天接着看，但已经找不到它在哪个库、哪一层目录」。最近播放能解决后者，收藏解决不了。

### 10.23.2 结论：换，而且这是首页第二重要的位置

| 维度 | 我的收藏（原） | 最近播放（新） |
| --- | --- | --- |
| 数据来源 | 用户手动添加，≤8 个 | `PlaybackProgress` 自动生成，无上限 |
| 维护成本 | 要删要置顶，加满 8 个就得取舍 | **零维护**，播过就有 |
| 覆盖范围 | 用户想到要收藏的 | **播过的一切**：跨库、跨课程、跨目录层级 |
| 会不会变旧 | 会。8 条常年不变，越看越旧 | 不会。永远按 `last_played_at` 排序 |
| 诉求对位 | 「我要跟这几个栏目」 | 「我昨天看到哪了」← 更高频 |

**收藏没有取消**，只是不再占首页第二块：入口变成横条右上角「我的收藏 ›」+ 底部 Tab Bar「收藏」。收藏屏、四处收藏入口（目录屏 / 播放页 / 列表星标 / 收藏屏）全部保留。

### 10.23.3 为什么它能覆盖「其他课程的视频课」

这是本节最关键的一点。**最近播放不读「最近更新」列表，它读播放历史表**：

```
SELECT ... FROM playback_progress
WHERE lib_enabled = 1
ORDER BY last_played_at DESC
LIMIT 12
```

- 不限定 `gid`：bb18、得到帆书、以后新增的第三个库，播过就进；
- 不限定时间窗：「最近更新」只看今天/昨天，最近播放可以追到三个月前那节课；
- 不限定层级：从目录树第 6 层点开的视频课，和首页列表第一条，在这里是**同级条目**；
- 不限定媒体类型：音频、视频混排，各自用「已听 / 已看」区分。

原型里 `第 3 课｜写作结构拆解 · 录屏` 和 `Day 12 · 案例精讲（直播回放）` 就是**首页最近更新列表里根本不存在的条目**，专门用来验证这一点。要找回它们，走收藏不行（没收藏过），走目录要翻 4 层——只有最近播放能一步到位。

### 10.23.4 音频 / 视频的文案与播放器分化

| 位置 | 音频 | 视频 |
| --- | --- | --- |
| 首页大卡 kicker | 继续收听 · 库名 | 继续观看 · 库名 |
| 大卡封面图标 | 音符 | 影片 |
| 卡片进度文案 | 已听 12:34 · 剩 29:42 | 已看 12:42 · 剩 18:38 |
| 完成态 | 已听完 · 可重听 | 已看完 · 可重看 |
| 播放页 | 波形图（音频可视化） | **16:9 画面区**（`SurfaceView`），波形隐藏 |
| 播放页副标题 | 库名 · 更新日期 | 库名 · 视频课 · 缓存地址已就绪 |

同一个 `PlayerActivity` + 同一个 `PlaybackProgress`，只换渲染面：音频用 `WaveformView`，视频用 `PlayerView`（`surface_type=surface_view`）。**不新增 Activity、不新增进度表**。

### 10.23.5 三个实现细节（不写进任务卡会返工）

1. **当前那条不重复**：正在播的条目已由顶部大卡承担，横条从第 2 条开始。否则同一条在首屏出现两次，用户会以为列表坏了。
2. **播放中不重建 DOM / 不 notifyDataSetChanged 整表**：只更新那一张卡的进度条宽度与文案。整表刷新会把横向滚动位置弹回起点，用户滑到第 5 张时进度一跳就回到第 1 张。
3. **无历史时整块隐藏**：不要留一个空的「最近播放」标题。首屏预算比「结构完整性」重要。

### 10.23.6 验收标准

- 首屏横条第一张卡 = **除当前播放外**最近一次播过的内容，不是固定写死的；
- 在目录树深处点开一节视频课 → 返回首页 → 该条排在横条第 1 位，文案用「已看」，大卡变「继续观看」；
- 同一条目不会同时出现在大卡与横条；
- 视频条目进播放页：画面区为 16:9，无波形；返回首页再进音频条目：波形恢复、画面区消失；
- 暗黑模式下卡片边框可见、进度条为强调色、第三张卡右端仍然是**淡出**而不是硬切；
- 播放历史为空时，横条与标题一起消失，下方筛选条上移，不留空白。

### 10.23.7 成本与排期

**不影响接口层、不影响 V6-d**，纯本地数据与布局：约 **0.5 天**（含视频渲染面切换 0.2 天）。排期不变，仍约 **4-4.5 周**。

唯一新增的存储字段：`playback_progress.last_played_at`（`Long`，毫秒）。已有表加一列 + 索引 `(last_played_at DESC)`，Room 里走一次 `Migration`，不需要清库。

## 10.24 视频浮窗 / 只听声音 / 后台继续（2026-11-07 13:46）

### 10.24.1 需求方原话

> 「视频是不是还可以加个浮窗播放，视频能转音频，在后台播放吗？有时候不方便看手机的，听视频中的音频。」

拆成三件事，但**第三件才是真需求**：不看屏幕也要把内容听完。浮窗是「半看」，转音频是用户以为的实现手段 —— 而实现手段不必是转码。

### 10.24.2 逐条结论

| 诉求 | 能不能 | 怎么做 | 代价 |
| --- | --- | --- | --- |
| 画中画浮窗 | 能，系统原生能力 | `enterPictureInPictureMode()`，Android 12+ 直接 `setAutoEnterEnabled(true)` | **0**，且**不申请悬浮窗权限** |
| 视频转音频 | **不需要转** | 关掉 video renderer（`TrackSelectionOverride` 禁用 `TRACK_TYPE_VIDEO`），音频照播 | **0**，秒切、不占存储 |
| 后台继续听 | 能，方案里本来就有 | 前台服务 + `MediaSessionService`，`foregroundServiceType="mediaPlayback"` | 已在排期内 |

### 10.24.3 为什么不要「转成 mp3」

假设一条 40 分钟 480p 课程：

| 做法 | 耗时 | 额外流量 | 额外存储 | 失败态 |
| --- | --- | --- | --- | --- |
| 下载 + 解码 + AAC 编码成 mp3 | 3-6 分钟（中端机） | 250MB（整条下完） | ~36MB（64kbps 单声道） | 转一半退出、源文件更新后失效、要清理 |
| **关视频轨，只播音轨** | **0 秒** | 0（同一条流） | 0 | 无 |

结论：**做「纯音频模式」，不做「音频文件」**。UI 文案也必须叫「只听声音」而不是「转成音频」——叫「转」会让用户以为占空间、会去找那个「转好的文件」，然后找不到。

### 10.24.4 必须说清的真相：省电，但不一定省流量

`/mbox/msg/streaming` 返回的是 HLS。是否省流量取决于主播放列表结构：

- **muxed**（音视频在同一个 variant 的分片里）→ 关视频轨**只省解码与 GPU**，分片照旧全部下载；
- **分离音轨**（主列表里有 `#EXT-X-MEDIA:TYPE=AUDIO` 独立组）→ 才能真正只拉音频，流量可降到 ~15%。

→ 新增实测项 **V6-e**：抓一次 `streaming?stream_type=M3U8_AUTO_480` 的 m3u8 主列表，看是否存在 `EXT-X-MEDIA:TYPE=AUDIO`。

- 有：纯音频模式可宣传「省 85% 流量」；
- 没有：只在 UI 说「不占屏幕、省电」，**不要承诺省流量**。

原型里提示条写的是「流量与画质无关」，就是按「未实测」的保守口径。

### 10.24.5 三态语义与生命周期

| 状态 | 画面 | 音频 | 前台服务 | 划掉最近任务 | 锁屏 / 通知栏 |
| --- | --- | --- | --- | --- | --- |
| 看画面 | SurfaceView 渲染 | 播 | 是 | 停止 | 可控 |
| 浮窗（PiP） | 系统 PiP 窗口 | 播 | 是 | 停止 | 可控 |
| 只听声音 | 渲染器释放 | 播 | 是 | **继续** | 可控 |

实现要点：

1. **PiP 里不要自绘控制条**：`PlayerView.setUseController(false)`，控制交给 `PictureInPictureParams.setActions()` 的 `RemoteAction`（暂停/播放、上一节、下一节，最多 3-5 个）。
2. **surface 类型换 `texture_view`**：`SurfaceView` 在部分 ROM 的 PiP 缩放动画里会闪黑边；`TextureView` 更稳。代价是略高功耗、不支持 DRM secure —— 本项目没有 DRM，可接受。
3. **`onStop()` 里不要 `release()`**：PiP 时 Activity 可能被销毁，但 `MediaSessionService` 必须活着，否则浮窗变黑块。
4. 纯音频模式：`player.setVideoSurface(null)` + 禁用视频轨，UI 切回波形；`MediaSession` 的 `playbackType` 保持 `TYPE_MOVIE` 不影响控制。
5. **`videoMode` 不落库**：它是会话级 UI 状态，下次进来默认「看画面」。落库的只有 `PlaybackProgress`。理由：用户上次用什么模式不重要，进度才重要。

### 10.24.6 版本与权限（易漏，直接抄）

```xml
<activity android:name=".PlayerActivity"
    android:supportsPictureInPicture="true"
    android:configChanges="screenSize|smallestScreenSize|screenLayout|orientation" />

<service android:name=".PlaybackService"
    android:foregroundServiceType="mediaPlayback"
    android:exported="true">
    <intent-filter><action android:name="androidx.media3.session.MediaSessionService"/></intent-filter>
</service>
```

- PiP：API 26+（Android 8.0），覆盖 ≥99%；自动进入 API 31+，31 以下在 `onUserLeaveHint()` 手动调；
- 前台服务：API 34+ 必须 `FOREGROUND_SERVICE_MEDIA_PLAYBACK` 权限 + `foregroundServiceType`；
- **不要**申请 `SYSTEM_ALERT_WINDOW`。国内 ROM 对悬浮窗权限有额外弹窗与风控，PiP 是系统级、无需该权限，能不用就不用。

### 10.24.7 验收标准

- 视频条目进播放页 → 三态切换条出现；**音频条目完全不出现**（高度 0，不留空隙）；
- 点「浮窗」→ 回到**进入前的屏幕**（不是固定首页），右下出现小窗，迷你播放器自动隐藏；点窗体或 ⤢ 回全屏；点 × 停止播放并关窗；

## 10.25 视频真实地址定位：`mboxvideo` 只是播放页，地址在 `/mbox/msg/streaming` 的 m3u8（2026-11-07 17:10）

需求方给出一次**真实视频**的两条 URL：一条 `#/im/session?fromId=654702226`（IM 会话页），一条 `GET /pfile/mboxvideo?...`（点开视频后被跳转到的播放页）。诉求："想获取文件库里视频的地址，现在只能跳转到这个 mboxvideo 页"。本节把两个 URL 拆开、纠正一处 ID 误判、并给出把播放页 URL 直接还原成可播地址的完整方法与探针。

### 10.25.1 两条 URL 是什么

| URL | 定性 | 关键判断 |
|---|---|---|
| `https://pan.baidu.com/disk/main#/im/session?fromId=654702226` | 网盘 SPA 的**前端路由**（`#` 片段，纯客户端），打开「通讯录里某个会话」 | `fromId` 是 9 位**通讯录会话/联系人 ID**，只决定前端打开哪个会话；**不参与播放**，不产生独立网络请求 |
| `GET /pfile/mboxvideo?type=2&to=…&from_uk=…&msg_id=…&fs_id=…&from_doc_lib=true&download_source=im&…` | pan.baidu.com 域下的 **HTML 播放器页**（新标签打开），**不是可播直链** | `from_doc_lib=true`/`download_source=im` 再次确证 IM 群组文件库体系；它是「壳」，真正取流发生在它内部（下节） |

> 结论：**「只能跳转到 mboxvideo」是必然的** —— 它不是视频地址，只是播放器页面。真正的地址要再从播放页内部那条 `streaming` 请求里取。

### 10.25.2 🔧 更正：ID 四件套（以本次真实 URL 为准）

此前文档（10.7.1 / 10.9.1 / 10.14.2 等）写「`to`（19 位）、`gid`（17 位）、`fromId`（9 位）是三个不同东西，且 `to≠gid`」。**本次真实 URL + 现有代码同时证明这条要更正**：

本次 `mboxvideo` URL 实测（逐个数字已核）：

| 参数 | 本次真实值长度 | 语义 | 是否参与取流 |
|---|---|---|---|
| `fromId` | **9 位**（654702226） | 通讯录会话/联系人 ID，仅 `#/im/session?` 前端路由用 | 否 |
| `to` | **17 位**（23519283863221172） | **就是库 `gid`**（`session_id = 04_ + gid`） | 是（拼 streaming 的 `to`） |
| `msg_id` | **19 位**（5155717895249185296） | 消息 ID（一条 IM 消息） | 是（拼 streaming 的 `msg_id`） |
| `fs_id` | **14 位**（19964726254273） | 文件 ID | 是（拼 streaming 的 `fs_id`） |
| `from_uk` | **10 位**（2390025356） | 分享者/上传者 uk（= owner） | 是（拼 streaming 的 `from_uk`） |
| `type` | `2` | 群组文件库常量 | 是 |

**更正点**：此前把「19 位」安在 `to` 上、把 `to` 与 `gid` 当两个东西 —— 实测是 **`to` 就是 17 位 `gid`，19 位的是 `msg_id`**。现有 App 代码也一直是这么用的（`PanApi.video` 里 `to = entry.gid`；`VideoStreamResolver.matches` 校验 streaming 的 `to == entry.gid`），二者一致。开发按「`to`=`gid`」写即可，不必再去找一个不存在的 19 位 `to`。**`fromId` 与播放无关**，只在打开会话页时用。

### 10.25.3 「视频地址」到底指什么

`/mbox/msg/streaming?` 返回的是一段 `#EXTM3U … #EXT-X-ENDLIST` 的 **HLS 播放列表（m3u8）**。分两种可能：

- **媒体列表（media）**：正文直接是 `#EXTINF` + 一串 `.ts`/`.m4s` 分片 URL；
- **主列表（master）**：正文是 `#EXT-X-STREAM-INF` + 各清晰度子列表 URL。

所以严格说「视频地址」有两层：**① m3u8 地址（streaming 接口返回的那个，喂 ExoPlayer 的入口）**；**② m3u8 里的分片 CDN 地址（真正搬运字节的签名 URL，~8 小时有效）**。App 只需拿到 ①（m3u8 正文 + 播放的分片 BaseURL），ExoPlayer 会自己拉 ②。

### 10.25.4 从 `mboxvideo` URL 直接拼 `streaming`（参数映射）

取流接口（C 级线索 + 与真实播放页参数高度吻合，仍属需实测契约）：

```
GET https://pan.baidu.com/mbox/msg/streaming
      ?from_uk=<from_uk>&to=<to>&msg_id=<msg_id>&fs_id=<fs_id>&type=<type>
      &stream_type=M3U8_AUTO_480
      &clienttype=0&app_id=250528&web=1
      （Header 需 Cookie 登录态；同源；建议带 X-Requested-With: XMLHttpRequest）
→ #EXTM3U …（HLS）
```

可选前置一条 `mediainfo`（拿 resolution / adToken，某些情况 streaming 需要 adToken / `isplayer=1` / `check_blue=1`，出现 `errno=133` 广告 token 分支时尤其要补）：

```
GET /mbox/msg/mediainfo?from_uk=<from_uk>&to=<to>&msg_id=<msg_id>&fs_id=<fs_id>&type=<type>&clienttype=0&app_id=250528&web=1
→ JSON（resolution / adToken …）
```

清晰度档位：`stream_type` 可试 `M3U8_AUTO_360/480/720/1080`；非会员可用档位受限。音频档 `M3U8_MP3_128` 是 C 级线索，需实测。

### 10.25.5 「只能跳转」的根因与两条解法

根因：`/pfile/mboxvideo` 是**新标签**打开的播放器页（内部 `window.open`/跳 `/mbox/streampage`），WebView 里点击后**没有 `WebChromeClient.onCreateWindow` 处理，新窗口被丢弃**，于是既进不了 `/mbox/streampage`、`VideoStreamResolver` 的 XHR 钩子也等不到 `/mbox/msg/streaming`，18 秒超时 → 看上去「只能跳转/只能看到百度播放器」。

两条解法，任选：

**解法 A（推荐，最干净）：不加载播放页，直接在 WebView 里同源 `fetch` streaming。**
播放页 URL 里五个参数已经够拼 streaming（10.25.4），用现成的 `MainActivity.load()`（同源 fetch + JS bridge 回传）发这条 GET，拿回 m3u8 正文即可，完全绕开新标签问题。

**解法 B（保底）：补 `onCreateWindow`，把新标签接进同一个/隐藏 WebView。**
`webChromeClient = object : WebChromeClient() { override fun onCreateWindow(...): Boolean { … WebView.WebViewTransport … } }`，让播放器新标签在同一 WebView 栈内打开，再靠 `VideoStreamResolver` 的 `/mbox/streampage` 钩子拦 `/mbox/msg/streaming`。改动大、且要处理多窗口生命周期，非必要不选。

> 无论 A/B，`VideoStreamResolver` 现有的封装都可复用：它已按 `fs_id` + `msg_id` + `to(==gid)` 校验候选，只是获取入口从「加载 player 页」改成「直接 fetch streaming」。解法 A 的 URL 用 `PanApi` 现有 `url()` 助手拼即可，body 无需。

### 10.25.6 浏览器里当场取证（已附探针）

不改代码、想立刻拿到这条视频的地址：在**已登录的 pan.baidu.com** 页面 F12 → Console，粘贴运行 `tools/probe_video_url.js`（把顶部 `MBOX_URL` 换成你地址栏里的 mboxvideo 完整 URL）。脚本会：先试 `mediainfo`，再 `fetch` `streaming`，打印 m3u8 正文、分片数量、首个分片绝对地址，并回显「视频地址 = 这条 streaming URL」。音频把 `STREAM_TYPE` 改成 `M3U8_MP3_128`。

> 探针只读、不落盘、不发第三方域，只用当前 Cookie 发同源 GET。

### 10.25.7 仍要实测/别写死的点

1. `streaming` 能否**脱离播放页直接 fetch**：可能需要 `adToken`（来自 mediainfo）、`isplayer=1`、`check_blue=1` 或播放页 `Referer`；若返回非 m3u8（JSON errno / 空），按 10.13.5 回退到解法 B 或抓官方 App。

### 10.25.8 对现有代码的落点

- `VideoStreamResolver`：`matches()` 校验 `streaming` 的 `to==entry.gid` **正确**；建议新增「解法 A 直取 streaming」分支，把 `videoResolver.start()` 从「loadUrl(player) 后等钩子」改为「`MainActivity.load(streamingUrl)` + 解析 m3u8」。

### 10.25.9 列表 → 地址：字段映射与二次实证（2026-11-07 17:15）

需求方随后给出了真实的 `GET /mbox/group/listshare` cURL：

```
GET https://pan.baidu.com/mbox/group/listshare?clienttype=0&app_id=250528&web=1
    &dp-logid=…&type=2&gid=23519283863221172&limit=50&desc=1
Header: Referer pan.baidu.com/disk/main, X-Requested-With: XMLHttpRequest, Accept: application/json
（无 bdstoken / time / sign，无请求体 → 只认 Cookie）
```

**① 二次实证：`gid` == `to`。** 这条 `gid=23519283863221172` 与本条 mboxvideo 的 `to=23519283863221172` **完全相同** → 库 `gid` 就是播放 `to`，10.25.2 的更正从「代码印证」升级为「跨接口实证」。

**② 无 Cookie 实测。** 直接跑（脱 Cookie）返回 `{"errno":-6, "show_msg":"请求超时，请稍后再试"}`（HTTP 200 但未登录）→ 印证该接口**只认 Cookie**，无 `bdstoken/sign`，必须在登录态页面里同源发。

**③ 列表响应 → streaming 四件套的映射。** `listshare`/`shareinfo` 响应结构为 `records.msg_list[]`，每条消息带 `msg_id` / `uk` / `file_list[]`，`file_list[]` 每项带 `fs_id` / `server_filename` / `path` / `isdir` / `size` / `category` / `md5`。因此：

| streaming 参数 | 从列表里取 |
|---|---|
| `to` | 库 `gid`（= 播放页 `to`，整库常量） |
| `msg_id` | `records.msg_list[i].msg_id`（消息级常量） |
| `from_uk` | `records.msg_list[i].uk` |
| `fs_id` | `records.msg_list[i].file_list[j].fs_id` |
| `type` | `2`（群组文件库常量） |

即：**列表接口一次就能把拼 streaming 所需的全部参数凑齐**，不必加载播放页。逐级下钻时 `gid`/`msg_id`/`from_uk` 不变（树级常量），只有 `fs_id` 随目录变。

**④ 两条「地址」路径（二选一，按需）**：
- **A. `dlink` 原始直链**：`har_report` 显示 `recentv2` / `shareinfo` 响应命中 `dlink`。若对本文库/文件返回非空，`dlink` 就是 `https://d.pcs.baidu.com/file/…` 的**原始 mp4 直链**（带 `User-Agent: pan.baidu.com` + Cookie 直连）。风险：引用式文件可能返回空 `dlink`；且是原始 377MB mp4，非转码，浏览器跨域受限。→ 这就是 V6-d 要实测的点。
- **B. `streaming` HLS 转码流**：用上面四件套拼 `/mbox/msg/streaming?...&stream_type=M3U8_AUTO_480` → m3u8 → ExoPlayer-HLS。**这是与网页播放器完全一致的官方播放链路，视频首选 B**（A 只在需要原始文件字节时用）。

**⑤ 探针**：新增 `tools/probe_listshare.js`（填 `GID` 即列库根，对每个 mp4 打印一条 `streaming` URL；填 `DRILL_*` 可下钻子目录），配合 `tools/probe_video_url.js`（从一条 mboxvideo URL 直接取 m3u8）覆盖「浏览列表」与「已知单条」两种入口。

> 别写死：`listshare` 的 `records.msg_list` 是「群分享消息列表」，库根第一层通常是「更新批次」而非文件；真正按年/月/主题/课程的目录要靠 `shareinfo` 逐级（只换 `fs_id`）下钻。`desc=1` 的排序字段、`type=2` 的确切语义仍未定，按响应为准。

## 10.26 通讯录「联系人」文件库：与群组同一套体系，入口/参数不同（2026-11-09 模拟器实测通过）

需求："通讯录里除了组，联系人也要管理；联系人也有文件库，应该和群是一样的接口。" 结论：**联系人和群组挂在同一套 IM 文件库体系上**，App 复用同一套 `PanEntry` + `CourseCache` + 目录浏览/取址流程，只用 `gid` 前缀区分来源：群组 `gid`=纯数字；联系人 = `contact-<uk>`。

### 10.26.1 接口差异（已实测）

| 环节 | 群组 | 联系人 |
|---|---|---|
| 列表发现 | `/mbox/group/list`（start/limit） | `/mbox/relation/getfollowlist`（channel/bdstoken/start/limit）→ `records[]`，字段 `uk` / `remark` / `display_name` / `nick_name` / `uname`，`black_flag!=0` 跳过 |
| 库根 | `/mbox/group/listshare`（gid, type=2, limit, desc, [last_msg_time]） | `/mbox/msg/sessioninfo`（`to_uk=<uk>`, type=2, [cursor]）→ `records.list[]`，每条 message 的 `filelist.list` / `xfilelist.list` / `file_list` 里是文件 |
| 下钻 | `/mbox/msg/shareinfo`（gid, type=2, limit, desc, msg_id, from_uk, fs_id, page, num） | `/mbox/msg/shareinfo`（**共用同一接口**，但 `type=1`、`to_uk=<会话对端uk>`、msg_id、from_uk、fs_id、page、num，不带 gid/limit/desc） |
| 取址 `/api/sharedownload` | `extra={type:"group", gid}` | `extra={type:"single", from_uk, to_uk}` |
| 取流 `/mbox/msg/streaming` | `to=<gid>, type=2` | `to=<会话对端uk>, type=1` |

**`to_uk` / streaming `to` 的规则**：`contactRecipient(viewer) = if (owner==viewer) <联系人uk> else viewer`，即「永远是这条消息的另一方」——消息由我发则对端=联系人，由联系人发则对端=我。
