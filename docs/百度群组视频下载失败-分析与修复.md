# 百度群组视频下载失败 · 根因分析与修复

> 结论先行：**失败不是网络问题，也不是 App 的 bug，是百度对群组共享库视频不返回原文件直链。**
> 修复方向已落地：视频改走 `/mbox/msg/streaming` 的 HLS 转码流，逐片下载后拼接成 `.ts`。
> 原始 mp4 只有一条路 —— 转存到「我的网盘」后走 `/api/download`。

---

## 1. 现象

群组（共享文件库）里点视频的「下载」：

```
群组大视频无法直接下载：网盘未返回原文件地址，请先转存到「我的网盘」再下载
```

而**同一个文件在线播放正常**，我的网盘里其它视频下载也正常 —— 只有「群组 + 视频」这一组合失败。

---

## 2. 根因（代码链路）

下载取址的分派在 `DownloadLogic.routeOf()`：

| 来源 | DownloadRoute | 取址接口 |
|---|---|---|
| 我的网盘 | `BAIDU_DISK` | `POST /api/download`（`sign1/2/3` 签名，返回 `dlink` 数组） |
| 群组 / 共享库 | `BAIDU_GROUP` | `POST /api/sharedownload`（`product=mbox`，返回 `list[].dlink`） |
| 夸克 | `QUARK` | 夸克私有接口 |

群组走的是 `DownloadLinkResolver` 的 `BAIDU_GROUP` 分支 → `PanApi.mediaLinkBody()` →
`POST /api/sharedownload` → `PanApi.parseMediaLink()` 取 `list[fs_id].dlink`。

**百度对这个接口的视频返回 `errno:0`，但 `list` 不是 JSON 数组，而是一段 4,504 字符的加密串。**
于是 `parseMediaLink` 的 `isFileLink` 校验失败，`DownloadLinkLogic.groupLinkIssue()` 判为
`ENCRYPTED_LIST`，抛出「请先转存到我的网盘」。

实测证据（本仓库内可复查）：

- `docs/百度网盘群组图片预览分析.md` §2.3、§8、§10.6
- `docs/媒体取址技术方案.md` §0、§4、§11（同一账号实测：视频走 streaming 拿到 200 片 m3u8；
  文档走 sharedownload 拿到明文 dlink）

关键点：**同一个接口对 PDF 返回明文数组 + 明文 `dlink`，对 mp4 返回加密串**。
所以这不是「接口坏了」，而是百度对群组视频刻意收紧了原文件直链 —— 网页端同样拿不到
（网页版的「下载」按钮在这种文件上也是走转存/客户端链路）。

---

> **补充（2026-11-22 二次实测）**：「转存后再下载」这条路的可用性已单独验证，
> 结论是**只对小文件成立**，大视频转存后直链仍被 31360 拦下。
> 详见 `docs/百度网盘转存后下载可行性-实测结论.md`。当前实现为三级降级：
> `sharedownload` → 转存拿原始文件 → HLS 转码流。

## 3. 三条通路对比

| 通路 | 拿得到什么 | 前提 | 代价 |
|---|---|---|---|
| `POST /api/sharedownload` | 视频：**加密串**（无地址）<br>文档/图片：明文 `dlink` | 登录 Cookie | 视频不可用 |
| `GET /mbox/msg/streaming` | **可用的 HLS 分片地址**（`expires=8h`，分片自带签名，拉片不需要 Cookie） | 登录 Cookie（只为主清单） | 产物是转码副本（TS 容器），清晰度受账号档位限制 |
| 转存 `/mbox/msg/transfer` → `/api/download` | **原始 mp4 直链** | 网盘空间 + 转存额度；非会员大文件仍可能限速 | 多一步、占空间 |

结论：想「点下载就拿到文件」，只能走第二条（转码流）；想「拿到原始 mp4」，只能走第三条。

## 4. 修复实现

新增/改动：

| 文件 | 作用 |
|---|---|
| `HlsPlaylistLogic.kt`（新） | m3u8 → 分片清单的纯解析：master/media 两种形态、相对地址解析、`#EXT-X-MAP` 初始化段、`#EXT-X-KEY` 加密识别 |
| `GroupVideoDownload.kt`（新） | 取清单（复用播放侧的重试语义）+ 逐片下载（单片重试 3 次）+ 顺序写暂存文件 |
| `VideoStreamResolver.kt` | 抽出 `PlaylistFetcher`（同步版取址核心）与 `playlistCookie()`，播放与下载共用一套重试逻辑；补齐 31341「转码排队中」的退避重试（原先只重试 133 广告门） |
| `DownloadLinkResolver.kt` | `resolve()` 返回 `Resolution`（`Single`＝单条 URL / `Playlist`＝分片清单）；群组视频在 `sharedownload` 拿不到直链时**自动降级到 HLS** |
| `DownloadCenter.kt` | 新增 `playlistJobs` 分片任务表：占并发槽、进度节流落盘、取消、下完置 `publishing` 复用原有 MediaStore 发布路径 |
| `DownloadLogic.kt` | `ts` → `video/mp2t` |

状态机（刻意复用现有那条，不新建）：

```
QUEUED ──resolve──> RUNNING(stagingName, publishing=false)   ← 分片下载中，进度写 bytesDone
                        └─下完─> RUNNING(publishing=true) ──pump──> publish() ──> SUCCESS
                        └─失败─> FAILED（删暂存文件，可重试）
```

几个必须守住的边界：

1. **并发槽**：分片任务计入 `usedSlots`，不会和系统下载任务抢跑超过 3 条。
2. **drain 恢复**：`drain()` 的「暂存文件找回」逻辑要跳过 `playlistJobs` 里的任务，
   否则会把正在下载的 `stagingName` 清掉；`drain()` 末尾的 `onIdle` 判定同样要把
   `playlistJobs` 算进去（分片任务不在 resolving/publishing 里），否则 JobService 提前收工、
   几百 MB 的后台下载失去保活。
3. **取消**：分片循环每片读一次 `AtomicBoolean`，取消后立刻停手，由下载线程自己收尾删文件
   （避免 cancel 与写盘竞态）。
4. **产物命名 + CC 归一化**：无 `#EXT-X-MAP` 初始化段时分片是 MPEG-TS，
   **裸字节拼接不是合法长 TS** —— 每片各 PID 的 `continuity_counter` 都从 0 重启，
   必须先过 `HlsTsNormalizer` 接成一条连续流（根因与实测见 §5.4），否则播放器会在
   每个分片边界重同步音视频时钟。有初始化段时是 fragmented MP4，按
   `.mp4` + `video/mp4` 落盘，且**不能**走 TS 归一化（moof 盒按 188 字节改会损坏）。
   容器与扩展名由 `DownloadLogic.playlistFileName` 统一决定，沿用源 `.mp4` 名字写 TS
   字节会让播放器判损坏。
5. **不做假成功**：分片加密（`#EXT-X-KEY` 非 NONE）、清单为空、多层 master 一律抛
   `GroupVideoDownload.Unsupported`，最终提示里带上「转码流也不可用：<原因>」，不静默产出坏文件。
6. **只认视频、不串台**：降级准入收敛在 `DownloadLinkLogic.shouldTryPlaylist(isVideo, issue)`；
   图片 / 文档 / 音频 / 我的网盘一律不碰转码流，`fs_id` 对不上（MISSING_FILE）也不降级。
   下载页的「转码流总长未知」「分片下载中」只认 `DownloadTask.playlistCopy` 标记，
   **不能拿 `bytesTotal <= 0` 当判据** —— 普通下载在 DownloadManager 未报 Content-Length
   时同样是 -1，否则图片/文档会被误标成分片任务。
7. **重试要还原记录**：分片副本的 `.ts` / `video/mp2t` 只属于本次任务；
   `DownloadLogic.requeue()` 按 `entry.name` 还原名字与 MIME 并清 `playlistCopy`，
   否则重试时若拿到明文直链，会把 mp4 字节存成 `.ts`。
8. **自动转存不能无差别触发**：三级降级里的「转存到我的网盘」是**写用户网盘**的操作，
   准入收敛在 `DownloadLinkLogic.shouldTryPrefetch` —— 只有「视频 + `list` 被加密」才尝试；
   非视频、空 list、`fs_id` 不匹配、无 dlink 一律直接落到 HLS，不碰网盘。
   提交前先拍专用目录快照，只认「快照后新增」的副本；删除前回读核对 `path -> fs_id`、
   删除后再回读确认，避免模糊匹配误删用户已有的同名文件。详见
   `docs/百度网盘转存后下载可行性-实测结论.md` §4。
9. **CC 归一化有状态且只走 TS 路**：`HlsTsNormalizer` 按 PID 跨全部分片累计计数，
   一个下载任务只能用一个实例、且必须覆盖第一片；`plan.initSegment != null` 时
   不创建实例。只改每包第 4 字节低 4 位：有 payload 的包 +1（4 bit 回绕）、
   只有 adaptation field 的包不递增、null packet 跳过；非 188 对齐或坏 sync
   整片原样放过。PCR / PTS / PES 数据一律不动，产物字节数不变。

### 5.3 真机暴露并修掉的一个真实缺陷

7 条任务同时向 `/mbox/msg/streaming` 取址时，有任务拿到 `31341 网盘仍在转码`，
而 `PlaylistFetcher` 早期实现**只对 AdGate 重试，31341 直接抛出** —— 一个 3 秒能自愈的
状态被写成了失败记录（实测文案：`…（转码流也不可用：网盘仍在转码，请稍后重试。）`）。

已修：`PlaylistFetcher` 对 `TranscodingPending` 增加退避重试（0.8s / 1.6s / 2.4s，最多 3 次，
合计 <5s），仍在 30s 总超时内。这类失败现在会自动恢复，不再需要用户手动「重试」。

### 5.4 真机产物复核：下载视频「画面和声音不同步」

发版后用户反馈：下载得到的 `.ts` 播放时音画不同步。取模拟器里已落盘的
`下载/拾课/…_2、店铺的选择：一扇没有门脸的小门洞.ts`（32,944,932 B / 660.7s）
到 Mac 上用 `ffprobe` / `ffmpeg` 复核。

| 检查项 | 结果 | 结论 |
|---|---|---|
| 音视频 PTS / PCR | 全程单调连续，无回跳、无大跳；视频起点 1.480s、音频 1.437s | 不是时间戳重置、不是分片乱序 |
| 帧数 / 时长 | 视频 16517 帧（25fps）、音频 30972 帧（46.875fps），660.68 / 660.672s | 数据完整，没有丢片 |
| `ffmpeg -v warning -c copy -f null -` | **76 个 `Packet corrupt (stream = 0)`** | 有 76 处边界异常 |
| TS 包层 | 76 次 PID 0（PAT）`continuity_counter` 重置；每片开头自带 SDT / PAT / PMT | 边界数 = corrupt 数 = 分片数 |
| `-v error` 全片解码 | 0 error | corrupt 是 warning 级，旧验收口径漏掉了它 |

**根因**：百度的每个 TS 分片是**独立可播的一段流**，各 PID 的 CC 都从 0 重新计数。
旧实现直接首尾相接，播放器在每个边界检测到 discontinuity → 判定丢包、把尚未结束的
PES 标记 corrupt、重新同步音视频时钟；76 个边界就是 76 次重同步，听感即音画不同步。
在线播放由 ExoPlayer 的 `HlsMediaSource` 逐片加载，知道分片边界，所以不受影响。

同一份文件的对照实验（只改字节、不重编码）：

| 处理 | corrupt 数 |
|---|---|
| 原样（当前产物） | 76 |
| 只剔除重复 PAT / PMT / SDT | 76 |
| **只把 CC 全局连续化** | **0** |
| 两者都做 | 0 |

→ 重复 PSI 表在连续 TS 里合法（广播流也周期性下发），**不是根因**；
`continuity_counter` 重置才是。修复因此只需重写每包第 4 字节低 4 位，
文件字节数、帧数、时长、PTS / PCR 全部不变。

**已落地**：`HlsTsNormalizer`（纯逻辑，无 Android 依赖）+ `GroupVideoDownload.download()`
逐片归一化；`HlsTsNormalizerTest` 9 条覆盖跨片连续、4 bit 回绕、adaptation-only
不递增、per-PID 独立、null packet、残字节、坏 sync 保守放过、确定性。
用 Kotlin 编译后的类重放同一份 32 MB 产物，与实验变体**逐字节一致**；
离线探针 `tools/group_video_download.js` 的 `DOWNLOAD=true` 路径同步修掉，
JS 版重放结果也逐字节一致。

🔴 不变式：**只有无 `#EXT-X-MAP` 的 TS 分片才归一化**；fMP4 分片是 moof 盒，
按 188 字节 TS 包改字节会直接把文件改坏。

**局限**：ffmpeg / ffprobe 是 demux 层的客观证据，不等于「每个播放器都同步得好」。
修复版 APK 已在模拟器覆盖安装冒烟，但**端到端重新下载一条视频未重放** ——
群组大视频下载会触发「自动转存」写用户网盘，不适合由脚本代跑；建议手动下一条验听。

## 6. 已知限制

- **产物是转码副本**：480p 档为主（非会员），不是原始 mp4；要原始文件请走转存。
- **码率会变，不等于丢片**：`videoPlaylist()` 用的是 `M3U8_AUTO_480` 自适应档，同一文件不同次
  取址可能拿到不同码率。实测 `3、人员的选择` 两次为 79,385,820 B / 43,960,040 B，
  `ffprobe` 时长均 905.8s、分辨率均 854×480，仅码率 701 / 388 kbps 不同；
  判断完整性要看时长 + 全片解码，不能只看字节数。
- **地址 8 小时过期**：m3u8 与分片都不能缓存，重下必须重新取址（当前实现每次任务都现取）。
- **总字节数未知**：HLS 分片不给总长，进度条在下载中是「不确定」态、文案写「转码流总长未知」，下完才回填精确值（已按此口径改造 UI，不再拿源文件大小当分母）。
- **断点续传未做**：进程被杀后整条重下（暂存文件名带 taskId+UUID，旧文件在重试时清理）。
- **加密分片不支持**：百度当前实测未启用，一旦启用会明确报错而不是产出坏文件。
- **产物仍是 `.ts`**：CC 归一化后已是单一连续流（ffmpeg 0 corrupt），但外部播放器
  对 MPEG-TS 的兼容仍参差；若个别播放器仍有音画不同步，下一步是把产物
  remux 成 MP4（需引入重封装能力，当前未做）。应用内播放走 ExoPlayer，不受此限制。

## 7. 现在就要拿到地址/文件（不改 App）

在**已登录**的 `pan.baidu.com` 页面 Console 里粘 `tools/group_video_download.js`：

1. 它会先用 `sharedownload` 复现「加密串」现象（把根因摆在眼前）；
2. 再用 `streaming` 拉 m3u8（master 自动选最高码率），打印分片数、时长、首个分片地址；
3. 把分片清单挂到 `window.__groupVideo`，并打印一份 `curl` 命令行清单（可离线/断点续下）；
4. `CONFIG.DOWNLOAD = true` 时直接用 `showSaveFilePicker` 流式写盘；脚本会逐片
   归一化 `continuity_counter`（与 App 同一套规则），得到一个音画同步的 `.ts`。
   `cat *.ts > raw.ts` 的命令行清单是**裸拼接**，后面给了 `ffmpeg -c copy out.mp4`
   的重封装兜底，别直接拿 `raw.ts` 当成品。

`CONFIG` 三个填法：粘贴播放页 `mboxvideo` 的完整 URL，或手填 `GID / FROM_UK / MSG_ID / FS_ID`。
