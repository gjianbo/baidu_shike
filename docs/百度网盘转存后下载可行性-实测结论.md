# 百度网盘：转存后能否下载 · 实测结论

> 结论：**「先转存再下载」只在部分文件上成立，不能当成通用主路径。**
> 实测同一账号下，小文件转存后直链可用，大视频转存后直链必然失效（31360）。
> 因此最终策略是：`sharedownload` → 转存拿原始文件 → HLS 转码流，三级降级。

---

## 1. 实验设计与结果

同一账号（uk 654702226，非会员）、同一签名要素（`sign1/sign2/sign3` + `timestamp`），
对两个文件分别走 `/api/download` 取 dlink，再直接请求 dlink：

| 文件 | 大小 | `expires` | `dstime` 偏移 | 带 Cookie 请求 dlink | 结论 |
|---|---|---|---|---|---|
| `拾课备份-….json` | 11.9 KB | **8h** | **0**（=timestamp） | **302 → CDN**，拿到真实字节 | ✅ 能下 |
| `5、表达的选择….mp4` | 160.7 MB | **1h** | **7200s**（早 2 小时） | **403 / 31360** | ❌ 不能下 |

`31360 = expire time out error` —— 不是 UA 问题，不是 Cookie 问题，是链接**签发即过期**。

### 排除项（都试过，都不影响结论）

| 变量 | 尝试 | 结果 |
|---|---|---|
| User-Agent | Mac Chrome UA / `pan.baidu.com` / 空 UA | 全部 403，无差异 |
| Cookie | 带上 BDUSS + STOKEN | 小文件 302 成功；大文件仍 31360 |
| 本地代理 | `--noproxy '*'` 直连 | 结果相同（排除沙箱 `http_proxy` 改写） |
| 时钟 | 本机与模拟器均为 CST，与 CDN `Date` 头一致 | 时钟正常，偏移是服务端行为 |
| 重复签发 | 连续三次取 dlink | 偏移固定 7200s，确定性复现 |

### 关键判据

偏移量固定为 **7200 秒**，且只出现在服务端「不愿意给直链」的文件上。
所以可用性可以**在发请求之前**判断：

```
skew = timestamp - dstime
可用 ⟺ skew ≤ 60s 且 expires ≠ "1h"
```

实现为 `GroupTransferLogic2.inspectDlink()`，两个实测样本都覆盖在单测里。

---

## 2. 为什么不能按文件大小预判

早期实现按 `size ≤ 64 MB` 猜。实测发现这不成立：

- 偏移只和大文件相关，但**没有中间样本**能定位真实阈值；
- 猜错的两个方向都亏：猜小 → 白转存一次几十 MB；猜大 → 本可下的文件被误杀走转码流。

所以改成「先转存，拿到 dlink 后用 `inspectDlink` 立刻判定」：
判定发生在**探测请求之前**，代价只是一次转存，不会产生无效下载。
判定为不可用时立即删除刚转存的副本（见 §4），把额度还回去。

## 3. 最终三级策略

```
群组文件下载
 ├─ ① POST /api/sharedownload
 │    文档/图片/音频 → 明文 dlink           ← 零成本，优先
 │    群组视频       → list 是加密串 ✗
 │
 ├─ ② 转存 /mbox/msg/transfer → 我的网盘 → /api/download
 │    准入：isVideo && issue == ENCRYPTED_LIST（shouldTryPrefetch）
 │    先查 /api/quota + 群组转存资格 + 空间余量，不足直接跳过
 │    dlink 形状可用 → 下载**原始文件** ✅
 │    dlink 形状不可用（skew>60s 或 1h）→ 删除副本，落到 ③
 │
 └─ ③ GET /mbox/msg/streaming 的 HLS 转码流
      逐片下载 + CC 归一化后拼接成 .ts（480p 转码副本），永远可用
```

顺序不能颠倒：

- ① 放最前，因为对文档/图片零成本，没必要为了「原始文件」先去占额度；
- ② 在 ① 失败后，是视频唯一的「原始文件」来源；
- ③ 是兜底，产物是转码副本，清晰度受限但不受额度与 31360 影响。

## 4. 实现要点

| 位置 | 作用 |
|---|---|
| `GroupTransferLogic2.parseQuota()` | 解析 `/api/quota` 的 `free/total/used`，缺字段判「未知」而非 0 |
| `GroupTransferLogic2.hasRoomFor()` | 空间闸门：需多留 `max(size*5%, 64MB)` 余量 |
| `GroupTransferLogic2.inspectDlink()` | 用 `expires` + `skew` 判直链可用性，探测前就认出来 |
| `GroupTransferLogic2.matchTransferred()` | `ondup=newcopy` 会改名成 `xxx(1).mp4`，按主体+扩展名+最接近 size 匹配 |
| `DownloadLinkLogic.shouldTryPrefetch()` | 自动转存的准入：只有「视频 + list 加密」才允许写用户网盘 |
| `GroupTransferLogic2.matchNewlyTransferred()` | 只认「目录快照之后新增」的条目，避免模糊匹配误配到用户原有同名文件 |
| `DownloadLinkResolver.prefetchOriginal()` | 二级通路：quota → 建专用目录/拍快照 → 转存 → 轮询落盘（6×1.2s）→ 取 dlink → 判形状 |
| `DownloadLinkResolver.discardTransferred()` | 转了但没用上时删除：限定专用目录、删前回读核对 `path -> fs_id`、删后再回读确认 |
| `DownloadLinkResolver.diskDirectLink()` | 与「我的网盘 → 下载」同一条链路，含形状预判 |

轮询上限 7.2 秒：转存是 `async=1` 异步落盘，超时就落回 ③，不让一个任务长时间占着并发槽。
超时会顺手清掉「本次同名且快照后新增」的副本，兜住 `errno=4` 之后副本晚到
（`errno=4` 是 QPS 上限，但文件可能已实际转存成功）导致的残留。

**写盘安全约束（审核补强）**：转存会自动往用户网盘写文件，因此
① 每个下载任务在进程内只尝试一次（`requeue` / 进程恢复不会反复转存）；
② 同一时刻只允许一笔自动转存在飞，避免并发任务互相把对方的副本当垃圾清掉；
③ 提交前必须先拿到一份可信的目录快照，拿不到就整条放弃，绝不带模糊基线写盘；
④ 删除只允许发生在 `/拾课转存` 专用目录，且必须「快照后新增 + 同名 + `path -> fs_id` 回读一致」。
局限：下载侧的互斥与 UI 手动转存的 `WriteGuards` 是两套锁，极端并发仍可能交叠；
UI 侧写操作由用户主动触发、频率低，暂不合并，若将来出现冲突再抽成全局单例。

## 5. 验证

- 单测：`GroupTransferLogic2Test` 17 条（quota 解析、空间闸门、两个真实 dlink 样本、未知形状、时钟漂移、改名匹配、目录排除、**目录快照只认新增条目**、**超时清理限定同名**）+ `DownloadLinkLogicTest` 的 `shouldTryPrefetch` 准入；全量 **584 条 0 失败**（审核补强后重跑）。
- `compileDebugKotlin / testDebugUnitTest / lintDebug / assembleDebug / assembleRelease` 通过；lint 0 error / 5 warning（全为历史文件）。
- ⚠️ 审核补强只跑了构建与 JVM 单测，**未在真机/模拟器重放转存链路**；自动写盘的行为改动上线前建议再实测一次。
- 模拟器实测（emulator-5554）：
  - 160.7 MB 群组视频 → 直链形状判定为不可用 → **不产生垃圾副本**，直接走转码流，落地 `.ts` 35.9 MB；
  - 网盘根目录经 `/api/list` 复核，只有原有 2 个文件，没有新残留。

## 6. 局限

- **大视频仍拿不到原始 mp4**：这是百度对非会员的直链限制，与空间无关。要原片只能升级会员或换源。
- **小文件阈值未精确测定**：只在 11.9 KB 与 160.7 MB 两个点采样；中间区间到底哪一档开始被加偏移，需要更多样本。当前实现不依赖这个阈值（改用 dlink 形状判定），所以不影响正确性。
- **转存会真实占用额度**：命中 ② 且直链可用时，副本会留在网盘，需用户自行清理（或后续加「下载完成后自动删除转存副本」的选项）。
- **`/api/quota` 的 `free` 有缓存可能**：实测返回实时值，但服务端不保证；空间判定只作粗筛。
