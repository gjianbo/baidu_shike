# 百度网盘 · 群组文件图片预览分析（缩略图 / 看图，不走下载接口）

> 版本：v1.0　生成日期：2026-11-10
> 适用：`pan.baidu.com` 新盘「我的群组 / 会话」页（`#/im/session?fromId=…`，登录态）
> 目标：群组（共享库 / 群文件）里的图片与视频，**不经过下载接口**，直接拿到可展示的缩略图/预览地址。
> 证据来源：真实登录态实测（R，2026-11-10，App 内隐藏 WebView 同源 `fetch`）+ 独立主机 `curl` 交叉验证；标 S 的为推断。
> 关联：`docs/百度网盘图片地址分析.md`（个人盘对照）、`docs/媒体取址技术方案.md`（群组 dlink / streaming）。

## 0. 结论速览

群组文件**不像个人盘那样「列表自带缩略图」**，但确实有不走下载接口的缩略图通道，分布在不同接口里：

| 接口 | 缩略图字段 | 形态 | 鉴权 | 实测 |
|---|---|---|---|---|
| `GET /imbox/file/recentv2` | 文件项 `thumb` | 对象 `{icon, url1, url2, url3}` | 需 Cookie | ✅ R |
| `GET /mbox/msg/shareinfo`（`fs_id`=**文件**） | `records[0].thumbs` | 对象 `{url1, url2, url3}`，另带 `dlink`/`resolution`/`duration` | 需 Cookie | ✅ R |
| `GET /mbox/msg/shareinfo`（`fs_id`=**目录**） | 无 | 返回子项数组，子项**不带**缩略图 | 需 Cookie | ✅ R |
| `GET /mbox/group/listshare` | **无** | 群根消息列表，压缩包外无缩略图字段 | 需 Cookie | ✅ R |
| `GET /api/sharedownload`（group 表单） | `list[0].thumbs` | 对象 `{url1,url2,url3}` | 需 Cookie | ✅ R（但 mp4 的 `list` 变加密串，见 §8） |
| `GET /aipic/image/filemetas` | `list[0].thumb` | 单条 URL | 需 Cookie | ✅ 仅个人盘；**群组返回空** ❌ R |
| `GET /api/list` | — | 个人盘专用，群组不适用 | — | ❌ |

> **关键点**：群组缩略图同样落在 `thumbnail0.baidupcs.com`，但签名类型是 **`rt=sn-gp`**（个人盘是 `rt=pr`），`fid` 用的是**文件所有者 uk**（不是自己的 uk）。**`size` 参数依旧不参与签名**，可自由换大尺寸 → 群组文件也能用「大缩略图」当看图大图，翻页零换链。

## 1. 群组文件的数据模型（先对齐参数）

会话页 `https://pan.baidu.com/disk/main#/im/session?fromId=<ID>` 背后是「群组/会话」体系，一条文件由这些键定位：

| 键 | 含义 | 来源 |
|---|---|---|
| `gid` | 群组 id（`/mbox/group/list` 的 `gid`） | 群列表 |
| `msg_id` | 该文件所属消息 id（群分享以"消息"为单位） | `listshare` / `recentv2` |
| `from_uk` / `fuk` | 文件所有者（发消息的人）的 uk | 同上 |
| `fs_id` | 文件 id | 同上 |
| `path` | 群内绝对路径，常为**百分号编码**（`%2F工作%2F…`） | 同上 |

实测该账号有 3 个群（其中一个 267 人的老群、两个课程群），`recentv2` 单页 30 条、`id=2` 再取 36 条，可翻页。

## 2. 三条可用通道

### 2.1 `recentv2`：群「最近更新」列表自带缩略图（最省事）

```
GET https://pan.baidu.com/imbox/file/recentv2
    ?clienttype=0&app_id=250528&web=1&channel=chunlei
    &id=1&session_id=04_<GID>
Cookie: 登录态
```

响应 `data.recentlist[i]` 的键（实测）：

```
avatar_url, category, fsid, fuk, gid, id, isdir, meta, msg_id,
parent_path, path, server_filename, share_root_path, thumb, time, uname
```

其中 **`thumb` 是对象**（这是最容易踩的坑：它不是字符串，`thumb.slice()` 会直接抛 `TypeError`）：

```json
"thumb": {
  "icon": "https://thumbnail0.baidupcs.com/thumbnail/<THUMB_ID>?fid=<OWNER_UK>-250528-<FS_ID>&time=<TS>&rt=sn-gp&sign=<SIGN>&expires=8h&chkv=0&chkbd=0&chkpc=&dp-logid=<DP_LOGID>&dp-callid=0&size=c60_u60&quality=100&vuk=<OWNER_UK>&ft=video",
  "url1": "…&size=c140_u90…",
  "url2": "…&size=c360_u270…",
  "url3": "…&size=c850_u580…"
}
```

实测分布（30 条）：

| 类型 | `thumb` |
|---|---|
| 目录（`isdir=1`） | `null` |
| `.mp4`（视频） | 对象，`ft=video`，`vuk=<OWNER_UK>` |
| `.pdf` | 对象，`ft=video`（页面首屏），`vuk=-` |
| `.mp3`（音频） | `null` |
| `.docx` | 无（未见 thumb） |

> 结论：**「最近更新」这一屏的缩略图是白送的**，一次请求拿 30 条，不用逐文件换链。这是群组预览里性价比最高的入口。

**补充（实测 R）**：同一条目里 `item.thumb` 与 `item.meta.thumbs` **内容完全相同**（`url3` 逐字节相等，同为 `size=c850_u580`、`rt=sn-gp`），是同一份数据的两个落点。30 条里 14 条带 `thumb`（其余是目录/音频）。
→ 这点很关键：现有代码的 `PanApi.previewUrlOf()` 读的是 `meta.thumbs`，**因此在群组 `recentv2` 上已经能命中预览地址**，不改解析就能出图；但若某接口只给 `thumb`（单数）而不给 `meta.thumbs`，`previewUrlOf` 的候选里没有 `item.optJSONObject("thumb")`，就会漏——群组侧解析要两个位置都兜。

### 2.2 `shareinfo`：单文件详情，`thumbs` + `dlink` 一次拿全

```
GET https://pan.baidu.com/mbox/msg/shareinfo
    ?clienttype=0&app_id=250528&web=1&channel=chunlei
    &msg_id=<MSG_ID>&from_uk=<OWNER_UK>&fs_id=<FS_ID>
    &page=1&num=100&type=2&gid=<GID>&limit=100&desc=1
```

**响应的 `records` 是数组**（不是 `{list:[...]}`，这点和旧文档不同）：

- `fs_id` 传**文件** → `records:[ {单个文件元信息} ]`，键含：

```json
{
  "server_filename": "03.｜定制功能…mp4",
  "isdir": "0",
  "mediaType": "video",
  "resolution": "width:1920,height:1080",
  "duration": 1992,
  "size": "342988543",
  "dlink": "<加密串 / 明文 URL，见 §8>",
  "thumbs": {
    "url1": "…&size=c140_u90&quality=100&vuk=<OWNER_UK>&ft=video&file_type=0",
    "url2": "…&size=c360_u270…",
    "url3": "…&size=c850_u580…"
  }
}
```

- `fs_id` 传**目录** → `records:[ 子项1, 子项2, … ]`，子项**只有** `fs_id / server_filename / isdir / path / size / 时间` 等基础字段，**没有 `thumbs`、没有 `dlink`**。
  → 所以「先列目录、再取缩略图」必须**对每个文件再调一次 shareinfo（传它的 fs_id）**，即 **1 请求 / 文件**。

**实测批量不可用**（R）：

| 尝试 | 结果 |
|---|---|
| `fs_id=<A>,<B>`（逗号） | 只返回 1 条（A） |
| `fs_id=<A>&fs_id=<B>`（重复参数） | 只返回 1 条（B） |

→ 没有多文件批量参数，只能逐个。

### 2.3 `sharedownload`：老下载链路的响应里也带 `thumbs`

```
POST https://pan.baidu.com/api/sharedownload?clienttype=0&app_id=250528&web=1&channel=chunlei&sign=&timestamp=
Content-Type: application/x-www-form-urlencoded
body: encrypt=0&uk=<MY_UK>&product=mbox&timestamp=&sign=&primaryid=<MSG_ID>
      &fid_list=[<FS_ID>]&extra={"type":"group","gid":"<GID>"}
```

- PDF：`errno:0`，`list[0]` 为**明文对象**，含 `thumbs{url1,url2,url3}`（`rt=sn-gp`）+ **明文 `dlink`**（`https://d.pcs.baidu.com/file/<MD5>…`）+ 空 `headurl`。
- mp4：`errno:0`，但 `list` 变成**一段加密字符串**（实测 4,504 字符），**不是 JSON 数组** → 从这条响应里取不到 `thumbs`/`dlink`（见 §8）。

> 结论：`sharedownload` 现在**不能再当作稳定的缩略图/直链来源**（视频直接给加密串）。要看图，用 2.1 / 2.2。

## 3. 群组缩略图 URL 与个人盘的差异

```
https://thumbnail0.baidupcs.com/thumbnail/<THUMB_ID>?fid=<OWNER_UK>-250528-<FS_ID>&time=<TS>&rt=sn-gp&sign=<SIGN>&expires=8h&chkv=0&chkbd=0&chkpc=&dp-logid=<DP_LOGID>&dp-callid=0&file_type=0&size=<SIZE>&quality=100&vuk=<OWNER_UK|->&ft=<video|image>
```

| 参数 | 个人盘（`/api/list`） | 群组（`sn-gp`） |
|---|---|---|
| `rt` | `pr` | **`sn-gp`**（share-group） |
| `fid` 中的 uk | **自己**的 uk | **文件所有者**的 uk |
| `vuk` | 自己的 uk | 所有者的 uk；**PDF 常为 `-`** |
| `expires` | `8h` | `8h`（`aipic` 那条是 `24h`） |
| `file_type=0` | 无 | shareinfo 的 `thumbs` 里有 |
| `ft` | `image` / `video` | `video`（**PDF 也是 video**，即页面首屏） |
| `size` 可改 | ✅ | ✅（见 §4） |

`aipic` 那条（仅个人盘）是另一种：`rt=yt`、`expires=24h`、`size=c200_u200`、`quality=91`、`vuk=-`，单条 `thumb` 字段。

## 4. `size` 换尺寸实测（群组 `rt=sn-gp`）

同一个群组 mp4 的 `url3`，只改 `size`（独立主机 `curl`，**无 Cookie、无 UA**）：

| `size` | HTTP | 字节 | 实际像素 |
|---|---|---|---|
| `c850_u580`（原 url3） | 200 | 58,922 | 850×478 |
| `c1600_u1600` | 200 | 138,749 | **1600×900** |

→ 与个人盘结论一致：**`size` 不参与签名，可任意放大（以源分辨率为上限）**；URL 自带签名，**跨设备/跨网络可用，不需要登录态**。所以群组也能做「大图预览 + 秒切」。

## 7. 请求数 / 性能对比

| 场景 | 方案 | 请求数 |
|---|---|---|
| 群「最近更新」一屏 30 条带图 | `recentv2` × 1 | **1** |
| 某目录 100 个文件都要缩略图 | 列表 1 次 + 每文件 `shareinfo` 1 次 | **101** |
| 只点开眼前这一张 | `shareinfo`(该文件) × 1 | **1** |
| 翻页看图（已拿到 big 尺寸 URL） | 0（CDN 直取字节） | **0** |

→ 落地策略：**列表先用 `recentv2`/缓存出图占位；用户点开某文件时再 `shareinfo` 补 `thumbs`，并用 `size=c2560_u2560` 预取前后各一张。** 不要为了宫格一次性打 100 次 `shareinfo`。

## 8. 已知问题与坑

1. **`thumb` 是对象不是字符串**：`recentv2` 里 `thumb` 为 `{icon,url1,url2,url3}` 或 `null`；直接当字符串处理会抛异常。
2. **PDF 缩略图不可靠**：`recentv2` 的 PDF `thumb`（`vuk=-`，`ft=video`）实测请求 `c850_u580` 返回 **10×580、2,722 B** 的窄条，不能当预览图。PDF 预览建议仍走 `docview/docpreview`（`/rest/2.0/docview/dlink`、`/mbox/fileinfo/preview`）。
3. **目录/音频没有缩略图**：目录 `thumb=null`，mp3 `thumb=null`（音频没有视觉封面）。
4. **`shareinfo` 的 `records` 是数组**，不是 `records.list`；旧代码若按 `records.list` 取会拿到 0 条。
5. **`shareinfo` 不支持批量**：逗号/重复参数都只回 1 条，只能逐个文件请求。
6. **`sharedownload` 对大视频返回加密 `list`**（4,504 字符的不可读串），同一接口对 PDF 却返回明文数组 + 明文 `dlink`。这条链路不能作为稳定的直链/缩略图来源。
7. **`aipic/image/filemetas` 只覆盖个人盘**（AI 相册/图片模块）：自己网盘图片返回丰富元信息 + `thumb`；群组 fsid 一律 `list: []`。
8. **`/api/list` 对群组无效**：群组是「消息 + 分享文件」体系，不是目录树，必须用 `mbox` 系列接口。
9. **路径是百分号编码**：`listshare`/`recentv2` 的 `path`、`parent_path` 常为 `%2F工作%2F…`，解析前要 URL 解码（注意 `Uri.decode` 不把 `+` 当空格）。

## 9. 与个人盘图片预览对照

| 维度 | 个人盘（`docs/百度网盘图片地址分析.md`） | 群组（本文） |
|---|---|---|
| 列表是否自带缩略图 | ✅ `/api/list?web=1` 每项 `thumbs` | ⚠️ 仅 `recentv2` 的 `thumb`；`listshare`/目录下钻没有 |
| 单文件拿缩略图 | 无需额外请求 | 需 `shareinfo`(文件) × 1 |
| 签名类型 | `rt=pr` | `rt=sn-gp` |
| `fid` 中的 uk | 自己 | 文件所有者 |
| `size` 可改 | ✅ | ✅ |
| 免 Cookie 直取 | ✅ | ✅ |
| 批量缩略图 | 天然支持（一次列表） | 不支持批量接口，需逐个 |
| 额外元信息 | 少 | `shareinfo` 额外给 `resolution`/`duration`/`mediaType` |

## 10. 落地建议（群组图片/视频预览库）

1. **入口**：进群 → 先 `recentv2` 拉一屏（30 条/页，可翻页），直接渲染 `thumb.url1/url2` 宫格，目录与音频留占位图标。
2. **点开**：对该文件的 `fs_id` 调一次 `shareinfo` 拿 `thumbs`，用 `PanApi.thumbResize(url3, "c2560_u2560")` 当大图；同时预取上下各一张。
3. **目录浏览**：`listshare`/`shareinfo`(目录) 只用来出文件名树；**文件行的缩略图等点击或滚动可见时再按需补**（懒加载 + 结果缓存）。
4. **缓存键**：`THUMB_ID@size@ft`（忽略 `sign/expires/dp-logid`），刷新列表后仍命中。
5. **失效自愈**：403/非 JPEG → 重新 `shareinfo`/`recentv2` 换新签名，不要复用旧 URL。
6. **PDF**：不要用 `thumb`；走既有 `docview`/`docpreview` 链路。

## 11. 未知与限制

- 群组里**没有实测到真正的图片（jpg/png）样本**：该账号 3 个群的可见文件只有 mp4/pdf/mp3/docx。图片走 `thumb` 是依据**同一字段结构**的推断（S），视频/PDF 已实测（R）。
- `sharedownload` 为何对 mp4 返回加密 `list`、对 pdf 明文，未定位触发条件（文件大小？`mediaType`？），只记录现象。
- `recentv2` 单页 30 条是否为固定上限、最大翻页深度未穷举。
- `thumb` 在 `recentv2` 与 `shareinfo` 中的 `dp-logid` 每次都变，`expires=8h`，未做跨 8 小时失效边界的实测。
- 所有接口无公开契约，字段会随版本变化，解析需容错（`thumb`/`thumbs` 缺失、为 `null`、`records` 形状变化都要兜住）。

## 12. 复现方式（不含凭据）

在已登录的 `pan.baidu.com` 页面上下文（App 隐藏 WebView 或浏览器 DevTools）执行：

```js
// 群列表 → gid
const gl = await (await fetch('/mbox/group/list?clienttype=0&app_id=250528&web=1&channel=chunlei&bdstoken=' + TOKEN + '&start=0&limit=20', {credentials:'include'})).json();
const gid = gl.records[0].gid;

// 最近更新 → thumb（注意是对象）
const rv = await (await fetch(`/imbox/file/recentv2?clienttype=0&app_id=250528&web=1&channel=chunlei&id=1&session_id=04_${gid}`, {credentials:'include'})).json();
const withThumb = rv.data.recentlist.filter(x => x.thumb && x.thumb.url3);
console.log(withThumb[0].server_filename, withThumb[0].thumb.url3);

// 换大图（浏览器外也能直接 curl，无需 Cookie）
const big = withThumb[0].thumb.url3.replace(/size=[^&]*/, 'size=c2560_u2560');

// 单文件详情 → thumbs + dlink
const m = rv.data.recentlist.find(x => x.isdir !== '1' && x.thumb);
const si = await (await fetch(`/mbox/msg/shareinfo?clienttype=0&app_id=250528&web=1&channel=chunlei&msg_id=${m.msg_id}&from_uk=${m.fuk}&fs_id=${m.fsid}&page=1&num=100&type=2&gid=${gid}&limit=100&desc=1`, {credentials:'include'})).json();
console.log(si.records[0].thumbs.url3);
```

## 13. 与现有代码的差距（2026-11-10 核对）

- **本次只产出文档，未改动任何代码**（分析用的临时脚本均在仓库外）。
- 现状：`PanApi.PanEntry` 已有 `previewUrl`，`previewUrlOf()` 通过 `meta.thumbs` / `thumbs` 多形态兜底，`largeImageUrl()` 把 `size` 换成 `c2560_u2560`。
  → **群组 `recentv2` 的最近列表已经能出预览图**（因为同一条目里有 `meta.thumbs`，`parseRecent → entry() → previewUrlOf()` 会命中）。
- 仍缺的三块：
  1. `previewUrlOf` 不认 `item.optJSONObject("thumb")`（单数）。`recentv2` 目前两者都有所以没暴露；只给 `thumb` 的接口会漏图。建议把 `thumb` 加进候选。
  2. **群组目录浏览没有缩略图**：`listshare` / `shareinfo`(目录) 返回的子项只有文件名基础字段；要宫格必须对每个文件再调一次 `shareinfo`(传它的 `fs_id`)，且**没有批量参数**（§2.2）。这是一次「N 请求」的取舍，应做懒加载 + 缓存，别一次打满。
  3. 群组 PDF 的 `thumb` 不可用（窄条，§8.2），PDF 预览仍应走 `docview/docpreview`。
