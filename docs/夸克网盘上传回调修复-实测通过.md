# 夸克网盘上传：真实客户端 HAR 复盘的完整实现（回调 400 / 43001 已解决）

> 输入：`/Volumes/mac/download/pan.quark.cn.har`（用户刚用**官网网页版**真实上传了一个 20,980,302 字节的 `ffmpeg.zip`，88 条请求）。
> 结论：**有两件事必须做，缺一个都会失败**：
> 1. 合并前必须先 `POST /file/update/hash {task_id,md5,sha1}`（登记内容哈希，否则回调 `content_hash` 为空 → 回调 400 → `203` → `43001`）。
> 2. **多分片（≥2 片）时，第 2 片起必须在 `auth_meta` 和 PUT 请求头里带 `X-Oss-Hash-Ctx`**（OSS 增量 SHA1 上下文），否则第 2 片 PUT 直接 `400 InvalidPart`。
> 单分片文件不需要 hash-ctx；两种都已本机实测验证。
> HAR 里含真实 `auth_info`/Cookie，属敏感数据，本文不记录其值。

`X-Oss-Hash-Ctx` 解码后（第 2 片的上下文 = 前 1 片 4MB 已哈希后的 SHA1 状态）：
```json
{"hash_type":"sha1","h0":"3144840977","h1":"230418468","h2":"1698707808",
 "h3":"1262534881","h4":"579051026","Nl":"33554432","Nh":"0","data":"","num":"0"}
```
- `h0..h4`：SHA1 五个 32 位状态字（无符号十进制字符串）。
- **`Nl` 是"已处理字节数 × 8"（单位 bit）**：33554432 bit = 4 MiB（正好第一片）。
- `Nh`：64 位长度的高 32 位（小文件为 0）；`data` 恒空、`num` 恒 "0"（因为每片 4MB 是 64 字节的整数倍，缓冲区为空）。

## 2. 关键细节（都能从 HAR 直接对出来）

- **callback** = `pre.data.callback` 这个对象直接序列化成**紧凑 JSON** 再 base64。HAR 里 `x-oss-callback` 解码就是：
  ```json
  {"callbackUrl":"sz3.api.aliyunpds.com/v2/file/upload_callback","callbackBody":"bucket=${bucket}&object_key=${object}&etag=${etag}&size=${size}&content_hash=${sha1}&mime_type=${mimeType}&...&upload_id=<uploadId>&mimeType=${mimeType}&..."}
  ```
  即：**没有引号二次包裹、不是哈希**。callbackBody 里有 `content_hash=${sha1}` —— 这就是为什么必须让 OSS 能填出 sha1（靠 `X-Oss-Hash-Ctx`）或让夸克从 task 拿到 sha1（靠 `update/hash`）。
- **XML 体**（HAR #71 原文，带换行）：
  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <CompleteMultipartUpload>
  <Part>
  <PartNumber>1</PartNumber>
  <ETag>"65E193AF45DC635701BB7D67C44A7B26"</ETag>
  </Part>
  ...
  </CompleteMultipartUpload>
  ```
  ETag 用 PUT 响应头原值（含引号）；`Content-MD5` 必须等于 `base64(md5(这段XML字节))`。
- **pre 响应**：`bucket` 动态（本次 `ul-sz`），`upload_url=http://pds.quark.cn`，OSS 主机=`{bucket}.pds.quark.cn`；`metadata.part_size=4194304`。
- **finish**：`{"obj_key","task_id"}` → 返回新 `obj_key`、`fid`、`md5`、`sha1`、`preview_url`（可用于回读校验）。
- **update/hash** 的 `md5/sha1` 是**整文件**的 32/40 位小写 hex（客户端本地算），`finish:true` 即秒传命中。

## 3. 实测：hash-ctx 到底是不是必须的（本机真实会话）

| 场景 | 结果 |
|---|---|
| **单分片**（小文件）：pre → update/hash → PUT 1 片（无 ctx）→ commit → finish | ✅ commit `200 {"Status":"OK"}`，finish `finish:true` |
| **多分片**（9MB，3 片）：pre → update/hash → PUT 1 片（无 ctx）→ **PUT 2/3 片（无 ctx）** | ❌ **PUT 2、3 返回 `400`**；commit `400 InvalidPart`；finish `43001` |

→ **结论：多分片必须给第 2 片起带 `X-Oss-Hash-Ctx`**（并且它要进 `auth_meta` 的签名串）。之前"X-Oss-Hash-Ctx 不需要"只对单分片成立，多分片会当场 400。官方客户端也是这么做的（HAR #46）。

## 4. 落地实现要点（给 `QuarkUploader`）

1. **顺序预扫描算哈希 + 每片边界状态**：边读文件边喂一个 SHA1 累加器，同时算整文件 md5/sha1；**每当凑满 `part_size`（4MB）就快照一份 SHA1 状态**（h0..h4、已处理 bit 数），记为 `ctx[i]`（第 i 片上传前要用前 i-1 片的状态）。
   - 这样可先预扫描一遍拿到所有 `ctx[i]`，再 **并行** 上传（ctx 只依赖该片之前的字节，和并发顺序无关）。
2. `update/hash`（整文件 md5/sha1）在合并前调用；`finish==true` 直接结束（秒传）。
3. 分片 N：
   - N=1：`auth_meta` 不含 `X-Oss-Hash-Ctx`，PUT 也不带。
   - N≥2：`auth_meta` 增加一行 `X-Oss-Hash-Ctx:<base64(ctx[N])>`（**大写 X，按字典序排在 x-oss-date 前**），PUT 请求头同时带 `X-Oss-Hash-Ctx: <同一个 base64>`。
4. 合并：XML + `Content-MD5` + `x-oss-callback`(callback 对象紧凑 JSON 的 base64)，`auth_meta` 用 §1.3 格式；**200 才算成功（203/400 = 回调或 MD5/签名不一致）**。
5. `finish {obj_key, task_id}`，用返回 `fid/preview_url` 回读确认。
6. `part_size` 用 `pre.metadata.part_size`（4MB）；`bucket`、`callback`、`upload_url` 全部动态取，不写死。
7. UA 必须与 `auth_meta` 里 `x-oss-user-agent` 完全一致（可选官方 `aliyun-sdk-js/1.0.0 Microsoft Edge 157.0.0.0 on OS X 10.15.7`）。

## 5. 错误码对照

| 现象 | 含义 / 处理 |
|---|---|
| 分片 N≥2 PUT `400 InvalidPart` | 缺 `X-Oss-Hash-Ctx`（或 ctx 与已传字节不匹配） |
| 合并 `203 CallbackFailed: Error status 400` | 缺 `update/hash`（content_hash 空）或 `Content-MD5` 不符 |
| `auth` `14001` | `auth_meta` 与实际请求头不一致（漏 `x-oss-callback`/hash-ctx，或 UA/date 不一致） |
| `upload/finish` `43001` | 合并未真正 200（InvalidPart / CallbackFailed 等） |
| `32004 file is too big` | 超单文件上限（实测 100GB） |
| `401/403` | Cookie 失效 |

---

## 6. 结论回顾

- HAR 完全印证了 `pre → (update/hash) → auth(part) → PUT(part, 带 ctx) → auth(commit) → CompleteMultipartUpload → finish` 这条链路。
- Q0 的 400/43001 = **漏 `update/hash`**；同时之前忽略的 **`X-Oss-Hash-Ctx` 对多分片是硬性要求**，两者都补上才能完整跑通大文件。
- 单分片可以省 ctx；多分片必须实现 ctx 序列化（SHA1 状态 5 字 + bit 长度）。
